# KidCare iOS — 보호자 앱 설계서

작성일: 2026-09-12
상태: 설계 승인됨, 구현 시작 전
대상: `ios/` (신규). 안드로이드 `app/` 은 이 작업에서 **한 줄도 건드리지 않는다.**

> **이 문서와 코드가 다르면 코드가 맞다.** 안드로이드 설계서(`2026-08-06-kidcare-design.md`)가
> 코드와 정반대인 서술을 두 번 배포했던 일이 있다. 고칠 때는 문장을 다듬지 말고 해당
> 파일을 열어 대조한 뒤 고칠 것.
>
> **Firestore 문서 스키마의 정본은 안드로이드다.** 이 문서가 아니라
> `app/src/main/java/com/kidcare/family/core/model/Documents.kt` 다.

---

## 1. 무엇을 만드는가

아이폰을 쓰는 **보호자**가 안드로이드 보호자 앱과 똑같은 일을 할 수 있게 하는 iOS
네이티브 앱. 같은 Firebase 프로젝트, 같은 가족 문서, 같은 초대 코드 체계를 쓴다.
아이폰 보호자는 새 가족을 만드는 것이 아니라 **기존 가족에 합류한다.**

기능 범위는 **안드로이드 보호자 화면과 동일**하다 — 페어링, 탭 다섯(지도·알림·관리·
예약·장소), 아이 선택기, 무응답 배너, 14개 언어.

### 만들지 않는 것 (명시적 제외)

- **아이 역할.** 아이 폰은 계속 안드로이드만 지원한다. iOS에서 불가능하거나 심하게
  망가지는 기능이 아이 쪽에 몰려 있다:

  | 아이 폰 기능 | iOS |
  |---|---|
  | 소리·진동 원격 전환 (예약의 핵심) | **불가능.** iOS에 무음↔벨 전환 API가 없다 |
  | 핸드폰 찾기 — 무음을 뚫고 사이렌 | 사실상 불가. Critical Alert 권한을 애플에 따로 신청·승인받아야 한다 |
  | 재부팅 후 자동 재시작 | 불가. 위치 이벤트로 간접 기동되는 것이 전부다 |
  | 포그라운드 서비스 상시 실행 | 개념 자체가 없다 |
  | 5초 경로 수집 | 되기는 하나 배터리와 심사 양쪽에서 대가가 크다 |

  아이 역할을 반쪽으로 내놓는 것보다 "아이 폰은 안드로이드"라고 분명히 말하는 편이
  낫다. 역할 선택 화면에 아이 버튼은 **보이되**, 누르면 안드로이드만 지원한다고
  알린다. 버튼을 지우지 않는 이유는 나중에 붙일 자리를 남겨두기 위해서이고,
  비활성(흐림)으로 두지 않는 이유는 흐린 버튼이 "왜 안 되는지"를 말해주지 않기
  때문이다.

- **푸시 알림(FCM).** 실시간 알림을 받으려면 Cloud Functions가 필요하고 그건 Blaze
  유료 요금제 전환을 뜻한다. **Spark 무료 요금제를 그대로 유지하기로 했다.** 대신
  iOS 알림 탭은 앱을 열었을 때 그동안 쌓인 사건을 보여준다. 이 제약은 화면 안에
  한 줄로 정직하게 적는다 — 안드로이드가 `alert_service_hint` 로 대가를 먼저 말한
  것과 같은 태도다.

- **`AlertService` 대응물.** 안드로이드 보호자 폰은 포그라운드 서비스가 Firestore를
  상시 구독해 알림을 받는다. iOS에는 이 방식이 존재하지 않는다. 흉내 낼 방법
  (백그라운드 페치, 무음 푸시)을 찾지 않는다 — 전자는 iOS가 하루 몇 번 돌릴지
  정하므로 "알림"이라 부를 수 없고, 후자는 결국 FCM이다.

- **위치 권한.** 보호자 화면은 위치 API를 한 번도 부르지 않는다(`guardian/` 전체에
  호출 0건). iOS 보호자 앱도 마찬가지다. 그래서 **이 앱이 요청하는 권한은 0개다.**
  이건 부수 효과가 아니라 지켜야 할 성질이다. 나중에 App Store 심사로 갈 때 가장
  까다로운 항목(가이드라인 2.5.4, 배경 위치)을 통째로 피한다.

### 배포 방식

당장은 가족 사용. 개발과 시험은 시뮬레이터와 본인 아이폰(무료 Apple ID)으로 한다.
가족에게 나눠줄 때 Apple Developer Program(연 $99)에 가입해 **TestFlight**로 보낸다.
**나중에 App Store 정식 출시를 염두에 두고 만든다** — 지금 당장 심사 자료를 만들지는
않지만, 심사를 막는 선택(권한 과다 요청, 개인정보 매니페스트 누락, 아이 동의 흐름
부재)을 하지 않는다.

## 2. 왜 이 방식인가 — 접근 세 가지를 비교한 기록

안드로이드 앱은 Kotlin 네이티브 + XML 뷰다(약 19,000줄). 공유할 수 있는 코드가 0인
상태에서 시작했다.

**A. 네이티브 Swift/SwiftUI + 로직 포팅 ← 채택**

보호자가 실제로 쓰는 순수 로직만 Swift로 옮기고(§6), 화면은 SwiftUI로 새로 쓴다.
안드로이드 앱을 전혀 건드리지 않으므로 잘 돌아가는 앱이 깨질 위험이 0이다. 옮겨야 할
"진짜 어려운 로직"이 744줄뿐이고 그 744줄에는 **이미 테스트 732줄이 붙어 있다**는 것이
결정적이었다. 대가는 로직이 두 벌이 된다는 것 하나다 — README의 "함께 고쳐야 하는 짝"
목록으로 관리한다.

**B. KMP(Kotlin Multiplatform)로 `logic/`·`core/` 공유 — 안 함**

로직을 한 벌로 유지하는 유일한 길이지만 두 가지가 걸렸다. 첫째, 동작 중인 안드로이드
앱을 모듈로 쪼개는 대수술이 필요하다. README가 "절대 건드리면 안 되는 것(조용히
망가지는 자리)"을 따로 한 절 잡아둔 프로젝트에서 이건 이득보다 위험이 크다. 둘째,
Firestore는 공식 KMP SDK가 없어 서드파티 래퍼에 의존해야 하는데, 이 앱이 실제로 쓰는
기능(서버 타임스탬프, 리스너 옵션, `hasOnly` 규칙에 맞춘 필드 통제)에서 막히면 그때는
되돌릴 곳이 없다.

**C. Flutter/React Native로 보호자 앱을 양쪽 공용으로 새로 — 안 함**

안드로이드 보호자 앱까지 버리거나 두 벌로 유지해야 하고, 네이버 지도는 서드파티
플러그인에 기대야 한다. 지금 앱의 완성도를 생각하면 명백한 손해다.

## 3. 아키텍처

### 저장소 배치 — 같은 저장소에 `ios/` 를 더한다

```
KidCare/
├─ app/                    안드로이드 (이 작업에서 변경 없음)
├─ ios/
│  ├─ KidCare.xcodeproj
│  ├─ KidCare/
│  │  ├─ Logic/            순수 Swift(Foundation만) — app 의 logic/ 짝
│  │  ├─ Core/             Firestore 접근만      — app 의 core/ 짝
│  │  ├─ Onboarding/       역할 선택 · 보호자 페어링
│  │  ├─ Guardian/         탭 다섯
│  │  └─ Resources/        Localizable.xcstrings(생성물) · Assets
│  └─ KidCareTests/        Logic 포팅 검증 — app 의 JUnit 짝
├─ i18n/                   14개 언어 원본 — 양쪽이 함께 쓴다
├─ tools/ios-strings.py    신규: i18n → .xcstrings 변환
└─ firestore.rules         양쪽이 함께 쓴다
```

별도 저장소로 쪼개지 않는다. `firestore.rules`, `i18n/*.json`, 문서 스키마, 개발일지가
한 곳에 있어야 "함께 고쳐야 하는 짝"이 안 깨진다. 저장소를 나누면 규칙 한 줄을 고칠 때
반대쪽 저장소를 열어볼 사람이 아무도 없다.

`settings.gradle.kts` 는 `:app` 만 include하므로 **`ios/` 가 생겨도 안드로이드 빌드는
아무 영향을 받지 않는다.**

### 모듈 경계 — 안드로이드와 같은 규칙

안드로이드의 설계 원칙 하나를 그대로 가져온다: **계산은 `Logic/` 에, Firestore는
`Core/` 에, 화면은 `Guardian/`·`Onboarding/` 에.** `Logic/` 이 Firebase도 SwiftUI도
UIKit도 import하지 않기 때문에 까다로운 계산을 전부 XCTest로 고정할 수 있다. 안드로이드
`logic/` 이 안드로이드 API를 안 보게 잘라둔 것과 같은 경계이고, 같은 이유다.

`Core/` 는 Firestore 접근만 한다. 화면은 Firestore를 직접 부르지 않는다.

### 기술 선택

| 항목 | 선택 | 왜 |
|---|---|---|
| 최소 버전 | iOS 17.0 | `@Observable` 을 쓸 수 있는 최저선. 실사용 커버리지는 사실상 전부 |
| 언어 | Swift 6 (Xcode 26.6 / iOS 26.5 SDK 확인됨) | |
| UI | SwiftUI | 새로 쓰는 코드에 UIKit을 고를 이유가 없다. 지도만 `UIViewRepresentable` 로 감싼다 |
| 비동기 | async/await | Kotlin 코루틴과 1:1로 옮겨진다 |
| 상태 | `@Observable` | Fragment + ListenerRegistration 구조를 뷰모델로 옮기는 데 가장 얇다 |
| 의존성 | Swift Package Manager | Firebase iOS SDK(Auth · Firestore) |
| 지도 | 네이버 지도 iOS SDK | 안드로이드와 같은 벤더 → 같은 NCP Key ID, 같은 좌표계·타일 |
| 프로젝트 파일 | Xcode 26의 동기화 폴더 그룹 | 파일을 추가해도 `.xcodeproj` 가 안 바뀌어 병합 충돌이 안 생긴다 |

## 4. 화면 — 무엇이 같고 무엇이 다른가

탭 다섯과 페어링, 아이 선택기, 무응답 배너를 **전부 그대로** 옮긴다. `dimens.xml` 의
격자 정본표와 "탭마다 눈이 갈 곳 하나"라는 규칙도 따른다. 색과 치수는 안드로이드
리소스에서 그대로 가져온다 — 눈대중으로 다시 고르지 않는다.

다른 곳은 정확히 네 군데다.

**① 알림 탭의 `AlertService` 스위치가 없다.** 그 자리에 제약을 한 줄로 적는다:
*"아이폰에서는 앱을 열었을 때 새 소식을 확인해요."* 문구는 `i18n` 원본에 새 키로
추가하고 14개 언어를 함께 채운다.

**② 권한 요청 화면이 통째로 없다.** 온보딩이 "역할 선택 → 초대 코드 입력 → 끝"으로
짧아진다. 안드로이드의 `PermissionActivity`·`PermissionStep` 은 아이 전용이라 대응물이
없다.

**③ 경로선.** 안드로이드 `GradientRouteOverlay`(진행에 따라 색이 변하는 선)는 네이버
iOS SDK의 다중 구간 경로로 같은 그림을 만든다.

**④ 역할 선택 화면의 아이 버튼.** §1의 "만들지 않는 것" 참고 — 보이되 누르면 안내한다.

### 탭별 대응표

| 안드로이드 | iOS | 비고 |
|---|---|---|
| `GuardianMainActivity` | `GuardianRootView` | 탭 컨테이너 · 아이 선택기 · 무응답 배너 |
| `MapTimelineFragment` (1,343줄) | `MapTimelineView` + 뷰모델 | 가장 큰 화면. 지도·타임라인·날짜 이동·실시간 보기·'지금 위치 확인' |
| `ControlFragment` (1,154줄) | `ControlView` + 뷰모델 | 명령 왕복과 "정직한 표시"(전달 중→완료, 60초 무응답) |
| `ScheduleFragment` (1,206줄) | `ScheduleView` + 뷰모델 | 하루 띠 UI · 공휴일 스위치 · 저장 후 `SYNC_RULES` 전송 |
| `PlaceFragment` (981줄) | `PlaceView` + 뷰모델 | 지도 한가운데를 좌표로 삼는 방식 그대로 |
| `AlertFragment` (302줄) | `AlertView` + 뷰모델 | 살구빛 하이라이트와 `read` 한 필드만 쓰는 계약 그대로 |
| `GuardianPairingActivity` | `InviteCodeView` | 코드 **발급** — 아이용·보호자용 둘 다 |
| `ChildPairingActivity` | `JoinFamilyView` | 코드 **입력** — 보호자 합류가 이 화면을 쓴다 |
| `RoleSelectActivity` | `RoleSelectView` | ④ 참고 |

**화면 규칙 두 개는 반드시 함께 옮긴다.** 안드로이드 주석이 근거를 남겨둔 것들이다.

- **탭을 바꿔도 지도를 다시 만들지 않는다.** 안드로이드가 `replace` 대신 show/hide를
  쓰는 이유가 여기 있다 — 지도를 새로 만들면 타일을 처음부터 다시 받고 부모가 옮겨둔
  지도 위치가 초기화된다. SwiftUI에서도 지도 뷰를 탭 전환에 살려 둔다.
- **알림 탭의 살구빛은 화면을 여는 순간의 안 읽은 ID를 따로 붙들어 칠한다.** 그냥
  "안 읽음"으로 칠하면 읽음 처리가 색보다 먼저 도착해 부모 눈에 아무것도 안 남는다.

## 5. 데이터

### 스키마의 정본은 안드로이드다

`Documents.kt` 의 문서 타입 12개(`FamilyDoc`, `MemberDoc`, `InviteCodeDoc`,
`ChildStatusDoc`, `TrailDoc`, `TrailPoint`, `SegmentDoc`, `CommandDoc`, `ScheduleDoc`,
`PlaceDoc`, `EventDoc`, `RingerSettingsDoc`)와 상수 셋(`CommandType`·`CommandState`·
`EventType`)을 Swift 구조체로 옮긴다.

**`Codable` 을 쓰지 않고 손으로 매핑한다.** `firestore.rules` 가 `hasOnly([...])` 로
필드 집합을 검사하기 때문이다. `Codable` 이 옵셔널 필드를 하나 더 내보내는 순간 쓰기가
통째로 거부되는데, 그 실패는 화면에서 "저장이 안 돼요" 한 줄로만 보여서 원인을 찾는 데
오래 걸린다. 안드로이드도 같은 이유로 손으로 맵을 만든다. 필드 집합 계약은 각
리포지터리 함수 안에 가둔다 — 화면은 ID 목록이나 값만 넘긴다(`EventRepository.markRead`
가 `read` 하나만 쓰는 구조가 본보기다).

### 아이폰 보호자는 대개 새 가족원으로 합류한다

익명 로그인이라 설치할 때마다 UID가 새로 생긴다. N:N 구조가 이미 `role = "guardian"`
초대 코드를 지원하므로 주된 흐름은 이렇게 된다:

```
안드로이드 부모 폰 → '보호자 초대' 코드 발급 → 아이폰에서 입력 → 같은 가족에 합류
→ 기존 아이·경로·예약·장소가 그대로 보인다
```

**안드로이드의 역할 선택은 보호자를 고르면 두 갈래로 갈린다** — "새 가족 만들기"는
코드를 **발급**하는 화면(`GuardianPairingActivity`)으로 가고, "가족에 합류"는 코드를
**입력**하는 화면(`ChildPairingActivity` 가 겸한다)으로 간다. iOS도 이 두 갈래를 그대로
둔다. 합류만 만들고 싶은 유혹이 있지만, 그러면 아이폰만 있는 집은 이 앱을 시작조차 할
수 없고 "전체 동일 범위"가 깨진다. `createFamily` 는 호출 한 번이라 아끼는 이득도 없다.

보호자는 합류한 뒤에도 **자기가 코드를 발급할 수 있어야 한다** — 아이를 한 명 더
연결하거나(`role = "child"`) 다른 보호자를 부를 때(`role = "guardian"`) 쓴다. 그래서
iOS도 발급 화면을 갖는다.

**이게 실제로 되는지 1단계에서 Firestore 에뮬레이터로 먼저 고정한다.** 규칙이 21KB고
README가 "가장 오래 걸린 부분"이라 적어둔 곳이라, 합류가 규칙에 막히는지를 코드보다
먼저 확인한다. 규칙을 고쳐야 한다면 그건 **안드로이드에도 영향이 가는 변경**이므로
별도로 알리고 승인을 받는다.

### 서버 시각과 오프라인

- **서버 시각 보정**: `FamilyRepository.serverNow` 와 같은 방식으로 옮긴다. 폰 시계를
  믿지 않는 자리가 어디인지는 안드로이드 구현이 정본이다.
- **오프라인**: Firestore iOS SDK의 기본 캐시를 쓴다. 안드로이드가 오프라인에서 보여주는
  문구·상태와 같은 것을 보여준다.

### 포팅이 맞았다는 증명 — 두 겹

눈으로 대조하지 않는다. 기계가 증명한다.

**첫째, 테스트를 먼저 옮긴다.** 위 표의 테스트 732줄을 XCTest로 먼저 옮겨 **빨간
상태**로 두고, 그걸 통과시키는 Swift를 쓴다. 테스트가 명세 역할을 한다. 구현부터 쓰고
테스트를 나중에 맞추면, 잘못 옮긴 구현에 맞춘 테스트가 나온다.

**둘째, 골든 파일로 두 구현을 맞댄다.** 테스트만으로는 "테스트가 안 보는 입력"에서
갈라지는 것을 못 잡는다. Kotlin 쪽에서 입력과 기대 출력을 JSON으로 뽑아
`ios/KidCareTests/golden/` 에 두고, Swift가 같은 JSON을 먹고 같은 답을 내는지 본다.
특히 미묘한 셋이 대상이다:

- `RoutePathRefiner` — 튐 제거와 평활은 문턱 하나가 어긋나도 그림이 달라진다
- `ScheduleResolver` — 자정을 넘는 규칙의 겹침 해석
- `KoreanHolidays` — 대체공휴일 배치 (2025~2030년치를 통째로 뽑는다)

골든 파일을 만드는 Kotlin 테스트는 `app/src/test/` 에 추가한다. **이건 안드로이드
코드를 건드리지 않는다는 원칙의 유일한 예외이고, `main/` 이 아니라 `test/` 에만
더한다** — 앱이 실제로 싣고 다니는 코드는 그대로다.

## 7. 다국어 — 번역은 다시 하지 않는다

`i18n/*.json` 14벌(각 346문장)이 이미 원본이다. `tools/ios-strings.py` 가 이걸 읽어
`Localizable.xcstrings` 하나를 만든다. 스크립트가 하는 일은 넷뿐이다:

1. 안드로이드 서식 `%1$s` → iOS 서식 `%1$@` (숫자 `%1$d` 는 그대로)
2. 안드로이드 이스케이프 풀기 (`\'` → `'`, `\n` 은 진짜 줄바꿈으로)
3. 키를 그대로 유지 — 안드로이드 `strings.xml` 과 같은 이름을 쓴다
4. iOS에만 있는 새 키(§4의 ①)를 원본 JSON에 먼저 추가한 뒤 생성

문장이 늘면 안드로이드와 iOS가 **같은 원본에서** 같이 는다. 화면에서 문장을 새로 만들
때 `.xcstrings` 를 직접 고치지 않는다 — 그건 다음 생성 때 사라진다.

## 8. 오류 처리

안드로이드 `ErrorText.errorMessage` 와 같은 자리를 만든다: 예외를 사람이 읽는 문장으로
바꾸는 함수 하나. 화면은 예외를 직접 해석하지 않는다.

- 네트워크 없음 / Firestore 거부 / 가족을 못 찾음 / 초대 코드 만료·오타 — 안드로이드가
  이미 문장을 갖고 있다(`i18n` 의 해당 키). 같은 키를 쓴다.
- **명령의 "정직한 표시"** 를 그대로 옮긴다: 보낸 뒤 그 명령 문서 하나를 따라가며
  `전달 중…` → `완료` 를 보여주고, 60초 안에 대답이 없으면 "애기폰이 응답하지 않아요"와
  마지막 신호 시각을 함께 띄운다. "완료"가 뜻하는 것은 **아이 폰이 done 이라고 적었다**는
  것 하나뿐이라는 안드로이드의 주의도 같이 옮긴다.
- **무응답 배너**는 판정 재료(언제 물었고 언제 대답이 왔는가)를 **폰 안에만** 둔다.
  서버에 두면 그걸 읽고 쓰는 것 자체가 무료 한도를 먹는다. 안드로이드와 같은 이유로 같게
  한다. 단, 값이 폰 안에 있으므로 **아이폰 보호자와 안드로이드 보호자의 배너는 서로 다른
  시점에 뜰 수 있다.** 이건 버그가 아니다 — 각자 자기가 물어본 것에 대해 말한다.

## 10. 사용자가 직접 해야 하는 준비

코드로 대신 못 하는 것들이다. **1~2번은 1단계 시작 전에 필요하다.**

1. **Firebase 콘솔에 iOS 앱 추가** → `GoogleService-Info.plist` 내려받기.
   `.gitignore` 에 넣는다 (안드로이드 `google-services.json` 과 같은 대우).
2. **네이버 클라우드 플랫폼 콘솔에 iOS 번들 ID 등록.** Key ID는 지금 것을 그대로 쓰고
   번들 ID만 추가하면 된다.
3. **번들 ID 결정** — `com.kidcare.family` 를 그대로 쓰는 것을 제안한다.
4. **Apple Developer Program 가입 ($99/년)** — **당장은 필요 없다.** 무료 Apple ID로
   시뮬레이터와 본인 아이폰에서 개발·시험이 다 된다(기기 설치는 7일마다 재서명). 가족에게
   TestFlight로 나눠줄 때, 즉 7단계에서 가입하면 된다.

## 11. iOS 고유의 알려진 제약

안드로이드 README의 "알려진 제약"에 더해 iOS에만 있는 것들이다. 받아들이기로 한 것이지
놓친 것이 아니다.

- **실시간 알림이 없다.** 앱을 열어야 새 사건이 보인다. §1 참고.
- **앱을 지우면 그 아이폰은 가족에서 빠진다.** 익명 로그인이라 재설치하면 UID가 바뀐다.
  안드로이드와 같은 제약인데, 다행히 **보호자는 초대 코드를 다시 받아 합류하면 된다** —
  아이 쪽처럼 "아이가 스스로 감시를 푼다"는 문제가 없어서 재연결에 설계 판단이 필요 없다.
- **무응답 배너가 안드로이드 보호자와 다른 시점에 뜰 수 있다.** §8 참고.
- **TestFlight 빌드는 90일 만료다.** 가족에게 계속 쓰게 하려면 분기마다 재업로드가
  필요하다. App Store 정식 출시로 가면 없어지는 제약이다.

## 13. 남은 미결정 사항

- **네이버 지도 iOS SDK의 배포 방식.** SPM을 지원하면 그대로 가고, CocoaPods만
  지원하면 CocoaPods를 설치해야 한다. 1단계 맨 앞에서 확인한다.
- **`firestore.rules` 가 새 보호자 합류를 막는가.** 1단계에서 에뮬레이터로 확인한다.
  고쳐야 하면 안드로이드에도 영향이 가므로 별도 승인을 받는다.
- **App Store 정식 출시 시점과 그때 필요한 자료**(개인정보처리방침 웹페이지, 심사용 테스트
  계정, 시연 영상, 아이 동의 흐름). 지금은 심사를 막는 선택을 하지 않는 선에서 멈춘다.
