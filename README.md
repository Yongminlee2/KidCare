# 우리아이 지킴이 (KidCare)

가족의 보호자 폰과 아이 폰에 같은 앱을 깔고, 한 가족 안에서 **보호자 N명과 자녀 N명**을 연결하는 자녀 관리 안드로이드 앱입니다. 엄마·아빠가 여러 아이를 함께 볼 수 있고, 화면 상단에서 한 아이를 골라 그 아이의 지도·알림·관리·예약·장소만 확인할 수 있습니다.

아이가 하루를 어디서 어떻게 보냈는지를 **지도 위의 선과 사람이 읽는 글**로 보여주고, 부모가 아이 폰의 소리·진동을 원격으로 바꾸거나 잃어버린 폰을 울려 찾을 수 있게 합니다.

> **화면 사진은 3단계 때 찍은 것입니다.** 지금 부모 폰 화면에는 여기 안 보이는 것이 둘 더 있습니다 — 아래쪽 **탭 다섯 개**(지도·알림·관리·예약·장소)와 지도 위쪽 카드의 **'지금 위치 확인'** 버튼. 다시 찍으려면 폰 두 대가 필요해서 아직 못 바꿨습니다.

```
🚶 이동 1.1km       10:10~10:50 · 40분
📍 ○○학원          10:50~11:40 · 50분
```

## 무엇을 만들고 무엇을 안 만들었나

**만든 것**

- 역할이 들어 있는 6자리 코드로 자녀 여러 명과 보호자 여러 명을 한 가족에 연결
- 보호자 화면 상단에서 특정 아이를 골라 지도·알림·관리·예약·장소를 아이별로 분리
- 아이 폰의 위치를 활동 인식과 실제 좌표 변화로 재확인해 수집하고, 실제 이동 중에는 5초 경로·머무름에는 5분 기준점만 로컬에 쌓아 하루를 **머무름/이동 구간**으로 요약
- 부모 폰에서 지도(경로선 + 마지막으로 확인한 위치)와 타임라인, 날짜별 조회
- 아이 폰의 소리·진동 원격 변경, 핸드폰 찾기, 시간대별 자동 전환
- 지도에서 찍은 장소에 아이가 도착하거나 나서면 부모 폰에 알림
- 부모가 아이 폰에 한마디 보내기, 부모가 맞추는 알람시계
- 배터리가 낮거나 권한이 꺼지면 부모 폰에 알림

**의도적으로 안 만든 것**

- **몰래 감시(아이콘 숨김).** 아이 폰에 앱 아이콘이 보이고, 알림줄에 "위치 공유 중"이 항상 떠 있습니다. 아이도 자기 상태를 볼 수 있습니다. 접근성 서비스로 다른 앱을 훔쳐보는 방식은 쓰지 않았습니다.
- **기기관리자 권한으로 앱 삭제 막기.** 오작동하면 폰 초기화까지 얽히는데, 아이 폰에 걸어두기엔 위험이 이득보다 큽니다. 그 위 단계인 기기 소유자 등록은 **아이 폰 공장 초기화**가 전제라 아예 하지 않기로 했습니다. 대신 부모가 물어봤는데 대답이 없으면 부모에게 알립니다.
- **WiFi 원격 제어.** 안드로이드 10부터 서드파티 앱은 WiFi를 켤 수 없습니다. 유일한 길인 기기 소유자 등록은 위와 같은 이유로 막혔고, 옛 API를 되살리려고 `targetSdk`를 내리면 위치 수집이 망가집니다.
- **통화·문자·앱 사용시간 감시.** 이 앱의 범위가 아닙니다.

**배포 방식**: 가족끼리 APK 직접 설치. 플레이스토어에 올리지 않습니다.

## 구조

```
com.kidcare.family
├─ logic/       순수 코틀린. 안드로이드 API 미사용 → JVM 단위 테스트 대상
│  ├─ InviteCode         6자리 초대 코드 생성·정규화·검증
│  ├─ LocationFilter     올릴 위치인지 판정 (정확도·이동거리·속도)
│  ├─ SegmentBuilder     위치 점 → 머무름/이동 구간
│  ├─ SegmentSummarizer  구간 → 시각·기간·거리 표기
│  ├─ ScheduleResolver   시간대 규칙 겹침·자정 넘김 해석
│  ├─ GeofenceEvaluator  장소 진입/이탈 판정 (히스테리시스·중복 억제)
│  ├─ TrailCodec         하루 문서 인코딩과 점 개수 상한(경로 축약)
│  ├─ MovementTrailFilter 이동 중 GPS 후보에서 흔들림·순간이동 걸러내기 + 변위 근거 판정
│  ├─ AdaptiveMovementDetector 활동 인식을 좌표·속도로 재확인해 수집 주기를 정함
│  ├─ RoutePathRefiner   그리기 전 단일 튐 제거·시간 공백 분리·오차 가중 평활
│  ├─ RouteWindows       경로선 창을 하루 전체에 빈틈없이 배분 (점 유실 방지)
│  ├─ LiveLocationRefiner 실시간 보기의 저정확도·순간이동 제거
│  ├─ ChildSelector      N명의 자녀 중 저장된 선택 유지·안전한 대체 선택
│  ├─ DisconnectRule     "물어봤는데 대답이 없다" 판정
│  └─ DayPicker          날짜 이동과 헤더 문구
├─ core/        Firestore 접근만
│  ├─ AuthGateway        익명 로그인 (동시 호출 가드)
│  ├─ FamilyRepository   N:N 멤버·역할별 초대·1:1 데이터 이전·서버 시각 보정
│  ├─ TrailRepository    하루 문서(trails/{dayKey}) 읽기/쓰기
│  ├─ CommandRepository  원격 명령 (전달 수단은 인터페이스 뒤에 숨김)
│  ├─ PlaceRepository    장소 (+ 저장하면 아이 폰에 다시 읽으라고 알림)
│  ├─ EventRepository    사건 쓰기·구독·읽음 표시
│  ├─ ScheduleRepository 시간대 규칙
│  └─ ErrorText          예외 → 사람이 읽는 한국어 안내
├─ onboarding/  역할 선택, 양쪽 페어링, 자녀 권한 안내
├─ child/       아이 폰 전용 — 상시 포그라운드 서비스와 그 부속
└─ guardian/    부모 폰 전용 — 탭 다섯(지도·알림·관리·예약·장소)과 알림 수신 서비스
```

**설계 원칙 하나**: 계산은 `logic/`에, Firestore는 `core/`에, 화면·서비스는 `child/`·`guardian/`에 둡니다. `logic/`이 안드로이드 API를 쓰지 않기 때문에 까다로운 로직(자정을 넘는 시간대 규칙, GPS 흔들림 속에서 "머물렀다"를 판정하는 것)을 전부 JVM 테스트로 고정할 수 있습니다.

### 데이터 흐름

```
[아이 폰 N대]                    [Firestore]                [보호자 폰 N대]
활동 감지 → 최대 30초 빠른 확인 → 실제 이동 확정 시 5초 경로
  → GPS 흔들림은 30초 확인, 정지는 5분, 등록 장소는 1분 주기
  → 이동점과 머무름 기준점을 폰 안에만 쌓음 (메모리 + 파일, 통신 0)

포그라운드 서비스의 리스너 ◄─────  commands/  ◄──────────  '지금 위치 확인'
  → 하루치를 다시 묶어
  → trails/{dayKey}       ──►  children/{uid}/trails/ ──►  타임라인 + 경로선
  → 현재 상태 덮어쓰기      ──►  children/{uid}  ────────►  선택한 아이 마커 + 배터리
  → state 갱신            ──►                  ────────►  "전달 중… → 완료"

장소 도착·이탈, 배터리, 권한
  → 사건 하나씩            ──►  events/  ──────────────►  알림 탭 + 시스템 알림
```

### N:N 가족 구조

가족 하나는 `members/{uid}`에 보호자와 자녀를 제한 없이 두고, 상태·경로·명령·예약·장소·소리 설정은 모두 `children/{childUid}` 아래에서 자녀별로 나눕니다. 초대 코드도 가족 문서의 단일 값이 아니라 `inviteCodes/{code}` 독립 문서이며 `role = guardian | child`가 들어갑니다. 그래서 자녀용 코드와 보호자용 코드를 동시에 발급해도 서로 역할이 바뀌지 않습니다.

기존 1:1 가족은 보호자 0.7 앱이 처음 열릴 때 가족 공용 예약·장소·소리 설정을 기존 자녀 아래로 한 번만 복사합니다. `schemaVersion = 2`가 기록된 뒤 새로 연결한 둘째 아이는 빈 자기 설정에서 시작하므로 첫째의 학교·무음 예약이 잘못 따라가지 않습니다.

현재 저장소는 Firebase Spark 무료 요금제를 그대로 사용합니다. 보호자가 늘면 각 보호자 화면이 읽는 횟수는 늘지만, 위치는 여전히 로컬에 쌓았다가 요청 시 하루 문서 한 건으로 올리므로 자녀 수 × 5초만큼 서버 쓰기가 폭증하지 않습니다. 나중에 자체 서버로 옮길 때의 REST 자원, 권한 경계, 배포 순서는 [`docs/nn-architecture.md`](docs/nn-architecture.md)에 정리했습니다.

원격 명령을 FCM 푸시가 아니라 **Firestore 실시간 리스너**로 전달합니다. 아이 폰은 위치 수집 때문에 어차피 포그라운드 서비스가 상시 돌고 있어서, FCM이 사주는 "잠든 앱 깨우기"가 여기서는 필요 없기 때문입니다. 덕분에 Cloud Functions(유료 요금제)를 쓰지 않습니다. 전달 수단은 인터페이스 하나 뒤에 감춰서, 나중에 FCM으로 갈아끼워도 부르는 쪽 코드는 그대로입니다.

**아이 폰은 주기적으로 아무것도 올리지 않습니다.** 부모가 물어봤을 때와 하루 한 번 안전 업로드, 그 두 순간에만 서버를 건드립니다. 그래서 부모 화면은 "지금 위치"라고 말하지 않고 "12분 전 확인한 위치예요"처럼 언제인지를 같이 적습니다. 왜 이렇게 바꿨는지는 아래 개발일지의 "무료 한도" 절에 있습니다.

## 개발일지

### 1~2단계 — 뼈대와 페어링, 위치 수집

앱 하나에 두 역할을 넣고, 부모가 만든 6자리 코드를 아이가 입력하면 연결되는 구조를 만들었습니다. 코드 알파벳에서 `0/1/O/I/L`을 뺐습니다 — 아이가 화면을 눈으로 읽고 손으로 옮겨 적는 코드라, 잘못 읽히면 연결이 실패하고 원인도 안 보입니다.

아이 폰은 상시 포그라운드 서비스가 위치를 받아 필터를 거칩니다. 이때는 50m 이상 움직였을 때만 통과시키고, 정확도가 100m를 넘거나 시속 200km를 넘는 이동은 GPS 오류로 보고 버렸습니다. (**두 숫자는 그 뒤 바뀌었습니다** — 지금은 25m, 그리고 정확도 문턱이 평소 50m·15분 굶으면 100m로 두 단계입니다. 통과한 점을 곧바로 서버에 올리는 것도 이제 안 합니다 — 아래 "무료 한도" 절.)

**이 단계에서 잡은 것들**

- **익명 로그인 동시 호출 버그.** 화면 두 개가 동시에 로그인하면 익명 계정이 두 개 생기고, 화면이 든 ID와 실제 로그인된 ID가 어긋납니다. 당장은 화면이 하나뿐이라 안 터지지만, 백그라운드 서비스가 도는 순간 **"위치가 그냥 안 올라가는데 이유를 모르겠는"** 형태로 나타났을 겁니다. 보안 규칙이 ID가 안 맞는 쓰기를 조용히 거부하기 때문입니다.
- **약속과 동작의 불일치.** 화면에 "연결이 끝난 뒤에는 바꿀 수 없습니다"라고 써놓고, 실제로는 버튼을 누르는 순간 역할이 잠겼습니다. 엄마가 자기 폰에서 실수로 `아이`를 누르면 앱 데이터를 통째로 지우는 것 말고는 되돌릴 방법이 없었습니다.

### 보안 규칙 — 가장 오래 걸린 부분

Firestore 보안 규칙만 **리뷰 3회, 재작성 2회**를 거쳤습니다. 자녀 관리 앱에서는 **아이가 곧 공격자**입니다. 아이는 폰을 손에 쥐고 있고 앱의 접속 키도 갖고 있어서, 앱을 거치지 않고 데이터베이스를 직접 두드릴 수 있습니다. 앱 코드에서 아무리 검사해도 규칙이 뚫려 있으면 소용이 없습니다.

실제로 잡힌 구멍들:

1. **모든 가족의 초대 코드가 새어나갔다.** Firestore에서 `read` 권한은 "문서 하나 읽기"와 "컬렉션 전체 목록 긁기"를 둘 다 엽니다. 이걸 착각해서 목록만 열린다고 주석까지 달아놨었습니다. 로그인만 하면 **전 가족의 초대 코드를 통째로** 받아갈 수 있었습니다.
   → 코드를 **문서 이름으로** 쓰는 별도 컬렉션(`inviteCodes/A2C4K9`)으로 분리했습니다. 코드를 정확히 아는 사람만 꺼내갈 수 있고 목록 조회는 완전히 막힙니다.

2. **아무나 남의 가족에 보호자로 등록할 수 있었다.** 멤버 생성 규칙이 "본인 ID로 쓰는가"만 검사했습니다.
   → 가족을 만든 사람만 보호자가 되고(`ownerUid` 대조), 자녀는 **자기가 입력한 코드를 증거로 제출**해 서버가 대조하도록 바꿨습니다.

3. **막았더니 옆문이 열려 있었다.** 위 둘을 고친 뒤에도, 가입한 아이가 **자기 문서의 역할을 `보호자`로 바꿔** 부모를 가족에서 삭제할 수 있었습니다. 만드는 문(create)은 잠갔는데 고치는 문(update)이 열려 있던 겁니다.
   → 역할과 가입 코드를 생성 후 불변으로 만들었습니다.

4. **명령 기능을 열면서 또 한 번.** 4단계에서 부모가 명령을 쓸 수 있게 규칙을 추가할 때, 기존 재귀 와일드카드를 남겨두면 **아이도 계속 명령을 쓸 수 있습니다**(규칙은 OR로 평가). 아이가 자기 폰에 `소리 켜기` 명령을 스스로 넣어 무음 예약을 무력화할 수 있었습니다.
   → 와일드카드를 없애고 하위 컬렉션을 하나씩 명시했습니다.

### 3단계 — 하루를 글로 바꾸기

위치 점 수백 개를 "몇 시부터 몇 시까지 어디에 있었고 언제 어디로 이동했는지"로 바꾸는 단계입니다.

**머무름 판정의 핵심은 "연속 2개" 규칙**입니다. 실내에서는 GPS 좌표가 수십 미터씩 흔들리고 가끔 수백 미터를 튑니다. 반경을 벗어난 점 **하나**로 머무름을 끊으면 학교에 있는 6시간이 수십 개 구간으로 쪼개져 타임라인을 읽을 수 없게 됩니다. 그래서 벗어난 점이 연속 2개 나와야 머무름이 끝납니다. 5분을 못 채운 정지(신호 대기 같은 것)는 이동에 흡수합니다.

**이 단계에서 잡은 것들**

- **무료 한도를 태울 뻔했다.** 구간을 다시 계산할 때마다 하루치 위치를 처음부터 다시 읽게 돼 있었습니다. 점이 쌓일수록 읽는 양이 늘어서 하루 최대 **3만 6천 건** — 무료 한도가 5만이고 그건 부모 폰 몫까지 합친 총량입니다. 넘으면 경고가 뜨는 게 아니라 **그날 나머지 시간 동안 앱이 그냥 멈춥니다.**
  → 아이 폰이 자기가 방금 올린 점을 메모리에 들고 있게 바꿔 **하루 2건**으로 줄였습니다.
- **하루가 항상 24시간은 아니다.** 하루의 끝을 "시작 + 24시간"으로 계산하고 있었습니다. 한국은 서머타임이 없어 지금은 안 터지지만, 가족이 해외에 나가면 **한 시간치 위치가 어느 계산에도 안 잡혀 영영 사라집니다.** 달력 기준으로 바꿨습니다.
- **아이가 권한 하나로 추적을 반쯤 무력화할 수 있었다.** 배터리를 아끼려고 "가만히 있을 땐 5분, 움직이면 1분"(지금은 5초)으로 전환하는데, 아이가 멈춰 있는 동안 활동 감지 권한을 끄면 "움직이기 시작했다"는 신호가 올 길이 없어 **밖에 나가 돌아다녀도 계속 5분마다만** 확인하게 됩니다. 부모 화면에는 5분 전 위치가 떠 있고 이유는 안 보입니다.
  → 권한이 사라진 것을 감지하면 곧바로 이동 주기로 되돌립니다. 배터리보다 위치 신뢰성이 먼저입니다.

### 무료 한도 — 가족 하나가 하루 1,100번을 썼습니다

무료(Spark) 요금제의 쓰기 한도는 **프로젝트 전체에서 하루 2만 번**입니다. 1,000가족을 담으려면 가족당 하루 20번이어야 합니다. 실제로 세어 보니 **1,100번**이었습니다 — 55배.

세어 보기 전까지는 아무도 몰랐습니다. 3단계에서 걱정한 것은 읽기였는데(위 "무료 한도를 태울 뻔했다"), 정작 벽에 먼저 부딪히는 쪽은 쓰기였습니다. 위치 한 점마다 문서를 하나 만들고 상태 문서를 한 번 덮어쓰니 하루 1,040번, 거기에 15분마다 도는 구간 재계산이 하루치 구간 문서를 통째로 갈아끼워 50번이 더 붙었습니다.

고친 방향은 **"주기적으로 올리는 것을 전부 없애고, 부모가 물어볼 때만 올린다"**입니다. 하루치를 문서 하나(`trails/{dayKey}`)로 합치고, 아이 폰은 위치를 폰 안에만 쌓다가 부모가 '지금 위치 확인'을 누를 때와 하루 한 번 안전 업로드에만 올립니다. 1,100번이 28~32번이 됐습니다.

**이 개편에서 잡은 것**

- **연결 끊김 배너가 정확히 반대로 동작할 뻔했습니다.** 그 배너의 판정은 "아이 폰이 30분 넘게 상태 문서를 안 고쳤으면 끊긴 것"이었는데, 그 상태 문서를 주기적으로 고치던 코드가 바로 이 개편에서 사라졌습니다. 그대로 뒀다면 **완전히 정상인 폰이 30분마다 무조건 끊긴 것으로** 보였을 겁니다. 기능이 없어지는 것보다 나쁩니다 — 부모가 몇 번 헛경보를 겪고 나면 진짜로 끊긴 날에도 그 문구를 안 읽습니다. 판정 재료를 "물어봤는데 대답이 없는가"로 바꿨습니다(`logic/DisconnectRule`).
- **35배 줄였지만 들어가지는 않았습니다.** 1,000가족 기준으로 여전히 1.4~1.6배 초과였고, 5단계가 이벤트를 더하면서 1.8~2.1배가 됐습니다. 반올림해서 "됐다"고 적지 않으려고 숫자와 계산 과정을 [`docs/known-issues.md`](docs/known-issues.md) 12·14번에 그대로 남겼습니다. 가족 하나가 혼자 쓰는 동안에는 한참 아래라, 지금은 막는 조건이 아니라 기록입니다.

### 5단계 — 장소 알림, 메시지, 부모가 맞추는 알람

부모가 지도에서 찍은 장소에 아이가 도착하거나 나서면 부모 폰에 알림이 오고, 한마디를 보내거나 알람을 맞출 수 있는 단계입니다.

**이 단계에서 잡은 것들**

- **새 보안 규칙이 옛 규칙 뒤에 숨을 뻔했다.** `events`에 "아이만, 자기 이름으로, 읽지 않은 상태로 만들 수 있다"는 규칙을 새로 넣었는데, 같은 컬렉션에 1단계 때 넣어둔 `allow create: if memberOf(familyId)` — 즉 가족이면 아무나 무엇이든 — 이 그대로 남아 있었습니다. **Firestore 규칙은 OR로 평가**되므로 새 규칙을 아무리 조여도 옛 블록 하나가 통과시켜 버립니다. 아이가 남의 이름으로 사건을 지어내거나, 미리 '읽음'으로 만들어 부모의 안 읽음 목록에서 지운 채로 넣을 수 있었습니다. 4단계에서 재귀 와일드카드로 똑같이 당한 자리라, 이번에는 옛 블록을 지우지 않고 **그 자리에서 고쳐 쓰고** 옆에 "블록을 하나 더 만들지 말 것"을 적어뒀습니다.
- **부모 폰 알림이 하루 18시간 조용히 죽을 뻔했다.** 아이 폰이 부모 폰을 깨울 수단(FCM)이 없어서, 부모 폰에도 `events`를 상시 구독하는 서비스를 하나 둡니다. 그 서비스의 종류를 `dataSync`로 적었는데 **안드로이드 15부터 `dataSync`는 24시간 중 6시간만 돌 수 있습니다.** 나머지 18시간은 서비스가 시스템에 끊기고, 화면에는 아무 표시도 없이 알림만 안 옵니다. 이 앱은 플레이스토어에 올리지 않는 사이드로드 전용이라 `specialUse`가 정당하게 쓸 수 있는 종류였고, 그쪽으로 바꿨습니다.
- **장소를 만들자마자 "도착했어요"가 떴다.** 처음에는 "그 장소에 대한 기록이 없는데 지금 안에 있으면 도착"으로 판정했습니다. 그런데 이 앱에서 그 상황은 새로 깐 폰이 아니라 **부모가 아이가 이미 있는 곳에 장소를 만드는 순간**이 압도적으로 흔합니다. 저장을 누르는 그 자리에서 "집에 도착했어요"가 뜨는데, 시각까지 '방금'으로 찍혀 세 시간 전에 있었던 도착을 지어내는 셈이었습니다. 지금은 처음 보는 장소는 **알리지 않고 상태만 조용히 심습니다.**
- **아무도 못 본 알림이 다음 진짜 알림을 잡아먹었다.** 같은 장소에서 5분 안에 두 번 알리지 않는 중복 억제가 있는데, 이 5분 시계를 "전환이 일어난 시각"으로 밀고 있었습니다. 그래서 부모가 도착 알림을 꺼둔 장소에서 아이가 들어갔다 나오면, **아무에게도 안 보인 도착이 시계를 되감아** 그 뒤의 진짜 이탈 알림이 사라졌습니다. 시계를 미는 기준을 "실제로 부모에게 알린 순간"으로 바꿨습니다.

**전수 리뷰에서 하나 더**

- **부모가 맞춘 알람이 회수될 수 있는 프로세스에서 울고 있었다.** 알람은 매니페스트 리시버 하나에서 시작하는데, 그 5분 동안 앱에 포그라운드 서비스가 하나도 없을 수 있습니다 — 아이가 위치 권한을 껐으면 위치 서비스는 스스로 멈추지만 걸어둔 알람 예약은 그대로 남기 때문입니다. 시스템이 그 프로세스를 회수하면 **소리가 조용히 끊깁니다** — 소리도 진동도 없이 그냥 멎습니다. 부모는 알람을 걸었고, 아이는 안 깼고, 어느 화면에도 아무 말이 없는 실패입니다. 우는 동안만 사는 작은 포그라운드 서비스를 두어 막았습니다.
- **"알림이 없어요"와 "못 불러왔어요"가 같은 화면이었다.** 목록 화면 셋이 전부 `목록이 비었는가` 하나로 빈 목록 문구를 띄우고 있어서, 보안 규칙을 아직 게시하지 않은 상태에서는 오류 한 줄과 "아직 온 알림이 없어요"가 **같은 크기로 동시에** 떴습니다. 부모는 가운데 큰 글씨를 읽고 조용한 하루로 이해하는데 실제로는 아무것도 못 읽은 상태입니다. 세 화면이 이제 못 불러옴 / 불러오는 중 / 정말 비었음을 구분합니다.

### 6단계 — 통신이 끊겼을 때, 막다른 골목, 그리고 배포용 빌드

오프라인 처리는 **새로 만들 것이 거의 없었습니다.** Firestore 안드로이드 SDK는 로컬 캐시와 쓰기 큐를 기본으로 켜 두기 때문입니다(SDK를 직접 열어 확인했습니다 — `persistenceEnabled = true`, 캐시 100MB). 이 단계가 실제로 한 일은 **그 사실을 코드에 적고, 화면이 거짓말하지 않게 만든 것**입니다.

핵심은 읽기와 쓰기가 정반대로 움직인다는 것이었습니다. 읽기는 캐시로 즉시 답하고, **캐시에 없으면 "없는 문서"로 답합니다.** 쓰기는 반대로 큐에는 즉시 들어가지만 **서버가 확인해 줄 때까지 완료되지 않고, 제한시간이 없습니다.** 이 비대칭 하나가 화면 여러 곳을 거짓말하게 만들고 있었습니다.

**이 단계에서 잡은 것들**

- **서버 시각을 재는 함수가 화면 두 개를 얼려 버렸습니다.** 부모 폰 시계와 서버 시계의 차이를 재는 코드가 있는데, 재는 방법이 **쓰기**였습니다(자기 멤버 문서에 서버 시각을 적고 즉시 다시 읽는 방식). 오프라인에서는 그 쓰기가 영영 안 끝나므로 이 함수도 안 끝납니다. 지도 상단 카드가 이 값을 기다리고 있어서 **그 뒤에 그려야 할 타임라인까지 통째로 안 그려졌습니다.** 오류도 스피너도 없이 빈 화면입니다. 제한시간을 두되 **시간 초과로 물러난 값은 캐시하지 않습니다** — 여기서 "차이 0"을 굳혀 버리면 초대 코드 만료가 다시 부모 폰 시계로 계산돼, 예전에 고쳤던 "만들자마자 죽은 코드" 버그가 되살아납니다.
- **"보냈어요"가 거짓말이었습니다.** 오프라인에서 명령을 보내면 쓰기가 큐에 들어간 것이지 아이 폰에 간 것이 아닙니다. 그런데 화면은 "전달 중…"에서 영영 안 벗어났습니다 — 60초 무응답 타이머가 **쓰기가 끝난 뒤에** 시작하도록 돼 있어서 그 타이머조차 시작하지 못했기 때문입니다. 지금은 15초가 지나면 "아직 안 갔어요 … 그 사이 상황이 달라졌을 수 있어요"라고 적습니다. 이때 "명령이 나갔다"는 전제로 화면을 고치는 콜백은 **일부러 부르지 않습니다** — 부르면 울리지도 않는 폰에 '소리 끄기' 버튼을 띄우고, 걸리지도 않은 알람을 "맞춰져 있어요"로 적습니다.
- **읽으면서 찾은 데이터 유실.** 보안 규칙이 사건의 발생 시각을 "서버 시각 기준 과거 24시간 안"으로 묶어 두는데, 큐에 밀려 있던 사건은 **일어난 시각**을 들고 있다가 연결이 돌아온 **지금** 도착합니다. 즉 **24시간을 넘겨 끊겨 있으면 그 초과분의 사건이 통째로 거부됩니다.** 30시간이면 처음 6시간 것이 사라집니다. 앱은 알아챌 수도 없습니다 — 거부는 쓰기를 기다리던 코루틴에만 전달되는데, 하루가 넘는 단절 동안 아이 폰 프로세스는 여러 번 죽었다 살아나고 큐를 다시 보내는 새 프로세스에는 기다리는 사람이 없습니다. 지도에는 그날 경로가 멀쩡히 그려지는데 "학교에 도착했어요"만 없는 모양이 됩니다. 이번 단계에서 고치지 않고(규칙 변경은 범위 밖) 조건과 숫자를 적어 뒀습니다.
- **"오류가 발생했습니다"만 있고 누를 것이 없는 화면들.** 여섯 가지 막다른 골목을 코드로 확인했는데 **셋은 이미 멀쩡했고 그대로 뒀습니다.** 진짜 막다른 골목은 셋이었습니다 — 첫 실행이 비행기 모드일 때(실패 문구만 있고 버튼이 없었습니다), 부모가 가족을 지웠을 때(아이 폰이 계속 "엄마 아빠랑 이어져 있어요"라고 말하고 있었습니다), 그리고 **구글 플레이 서비스가 없거나 옛 버전일 때**. 마지막 것은 저장소 어디에서도 확인한 적이 없었습니다 — 없으면 위치와 지오펜스가 **콜백도 예외도 없이** 죽는데, 서비스는 떠 있고 알림줄도 그대로여서 부모 화면의 마커만 멈춥니다.
- **아이콘의 새싹이 사라졌습니다.** 앱에 아이콘 선언 자체가 없어 기본 로봇이 떠 있었습니다. 새싹이를 적응형 아이콘 규격에 맞춰 앉히고 배경을 지도 핀과 같은 하늘색으로 골랐는데, **실제 크기(48dp)로 그려 보니 잎이 보이지 않았습니다.** 잎 색과 배경색이 색상만 다르고 밝기가 거의 같아서, 작아지면 두 색이 하나로 뭉쳐 새싹이가 그냥 웃는 얼굴이 됩니다 — 아이콘을 만든 이유가 정확히 사라지는 실패입니다. 더 밝은 배경으로 바꿔 잡았습니다. **"되겠지"로 넘기지 않고 실제 크기로 그려 봤기 때문에** 보인 것입니다.
- **R8이 모델의 게터 스무 개를 지웠습니다.** 배포용 빌드에서 코드 축소를 켰는데, Firestore가 문서를 데이터 클래스로 바꿀 때 쓰는 게터들이 **난독화된 게 아니라 통째로 사라졌습니다**(쓰는 데가 없으니 지운 겁니다). 인자 없는 생성자도 함께 사라져서, 객체를 만들 수조차 없는 상태였습니다. 이 고장은 크래시가 아니라 **빈 화면**입니다 — 앱은 멀쩡히 돌고 모든 화면이 비어 보입니다. 보호 규칙을 하나씩 지워 보며 각 규칙이 정말 필요한지 확인했고, **아무것도 안 하는 규칙 하나는 도로 지웠습니다**(하는 일 없는 보호 규칙을 남기면 결국 전부 다 지키게 됩니다). 리소스도 7,000개에서 4,775개로 줄었는데, 앱이 직접 선언한 343개 중 사라진 것은 참조가 하나도 없는 4개뿐임을 이름으로 확인했습니다.

### 후속 개선 — 화면 재설계와 5초 이동 경로 (2026-08-08)

기능 구조는 유지하면서 런처 아이콘, 역할 선택, 아이 홈, 보호자 탭 다섯 개의 색상·아이콘·간격을 한 체계로 다시 맞췄습니다. 지도는 아이 위치를 더 가까이 보는 줌 18을 기본으로 하고, 날짜 한 줄만 남긴 채 이동 기록을 접고 펼칠 수 있게 바꿨습니다. 기존 지도는 하루 원시 위치점이 문서에 있는데도 구간 끝점만 연결해 골목과 회전이 잘렸습니다. 이제 저장된 원시점을 시간순으로 이어 실제 경로를 그립니다.

실제 이동으로 확정된 동안 위치 후보를 **5초마다** 받습니다. 활동 인식이 이동이라고 알려도 곧장 경로로 쓰지 않고, 정확도 30m 이내의 세 점이 10초 이상 지속되며 오차 반경의 두 배 또는 순변위 30m를 벗어나는지 다시 확인합니다. 증거가 없으면 30초 저주기 확인으로 내리고, 이동 확정 뒤에도 60초간 제자리면 다시 내립니다. 집·학교처럼 등록한 장소 안은 1분 주기 머무름으로 처리하고 OS 지오펜스가 이탈을 깨웁니다. 활동 인식 정지는 5분 주기입니다. 부모가 **실시간 보기**를 누른 동안만 이 분류와 별도로 2초 고정밀 위치를 서버 상태 문서에 보내며, 세션은 최대 10분입니다.

경로 파일에는 실제 이동점과 머무름의 시작·5분 기준점만 남깁니다. 따라서 학교 안의 작은 움직임과 GPS 흔들림은 초록 선처럼 이어지지 않지만, 실제 보행·자전거·차량 이동은 확정 직전 후보점까지 되살려 출발 구간을 보존합니다. 30m보다 부정확한 경로점, 5초 미만 간격, 오차 반경 안 흔들림, 시속 200km를 넘는 순간이동도 기존 필터에서 한 번 더 제외합니다.

아이 폰의 로컬 원본에는 2,000점 제한을 걸지 않습니다. Firestore의 하루 문서만 1MB 상한을 피하려고 최대 2,000점을 유지합니다. 초과한 날은 예전처럼 오래된 점을 버리지 않고, 출발·도착과 큰 회전을 우선 보존하는 경로 축약으로 하루 전체를 담습니다. 머무름·이동 요약은 축약하기 전 로컬 원본 전체로 계산합니다. 따라서 서버 쓰기 횟수는 부모가 확인할 때와 하루 한 번 안전 백업 때 하루 문서 한 건이라는 기존 구조를 그대로 유지합니다.

검증은 보호자·아이 역할의 갤럭시 두 대에서 진행했습니다. 아이 폰 서비스 로그에서 `이동 확인 5초` 요청과 재시작 복구를 확인했고, 실내 정지 상태에서 경로 파일이 불어나지 않는 것을 확인했습니다. 적응형 이동 판정·실시간 위치 보정·경로 보정까지 포함한 단위 테스트 **146개**, Android Lint, 난독화 릴리스 빌드가 통과했습니다. 남은 실사용 확인은 실제 보행·차량 경로의 모퉁이 품질과 하루 배터리 소모입니다.

### 3D 아이콘과 화면 마스코트 통일 (2026-08-08)

선택한 3D 캐릭터를 런처 아이콘으로 적용하고, 같은 얼굴·민트색 지도 핀·새싹·하트 형태를 유지한 투명 배경 마스코트를 별도로 제작했습니다. 역할 선택, 아이 홈, 연결, 권한 안내, 메시지, 휴대폰 찾기, 초기 로딩 화면까지 일곱 화면의 기존 평면 마스코트를 이 이미지로 교체했습니다.

작은 버튼 아이콘과 지도 마커는 3D로 바꾸면 실제 표시 크기에서 형태가 뭉개지므로 기존 벡터를 유지했습니다. 기능 코드와 화면 구조는 건드리지 않았으며, 단위 테스트와 축소된 릴리스 빌드를 통과한 뒤 갤럭시 실기기에 `versionName 0.6`을 덮어 설치해 투명 배경·잘림·표시 크기를 확인했습니다.

### 보호자 N명 × 자녀 N명 가족 구조 (2026-08-10)

1:1로 고정돼 있던 것은 Firestore 경로가 아니라 초대와 화면 선택이었습니다. 기존에도 `members/{uid}`와 `children/{childUid}`가 있었지만 초대 코드는 자녀용 하나뿐이었고, 보호자 화면 다섯 개가 모두 첫 번째 자녀 uid만 집었습니다. 초대 문서에 역할을 넣어 보호자도 기존 가족에 참여하게 만들고, 메인 화면 상단 자녀 선택을 지도·알림·관리·예약·장소 전체의 단일 기준으로 연결했습니다.

예약·장소·소리 잠금은 가족 공용에서 `children/{childUid}` 아래로 옮겼습니다. 기존 1:1 데이터는 첫 자녀에게 자동 이전하고, 이동이 끝나기 전 아이 폰은 구버전 경로로 물러납니다. 마지막 요청 시각, 알람 기억, 전달 대기 깃발도 자녀 uid별로 나눠 둘째 아이의 응답이 첫째 아이의 연결 끊김 배너를 지우는 일을 막았습니다.

보안 규칙은 자녀용·보호자용 코드의 역할 일치, 자녀별 예약·장소 쓰기, 다른 자녀 데이터 읽기 차단을 로컬 Firestore 에뮬레이터에서 실제 허용·거부 요청으로 검증했습니다. 선택 규칙 4개를 더해 단위 테스트는 125개가 됐습니다. Firebase 규칙·인덱스를 먼저 게시한 뒤 가족의 모든 기기를 0.7로 맞춰야 합니다.

### 운영 Firebase N:N 실기기 재검증 (2026-08-12)

갤럭시 탭 S7을 보호자, 갤럭시 A16을 자녀로 두고 앱 데이터를 초기화한 뒤 축소된 0.7 릴리스 APK를 새로 설치했습니다. 로컬 서버 우회 없이 운영 Firebase에서 가족 생성, 새 번호 발급, 자녀 가입, 권한 설정, 포그라운드 위치 서비스, `지금 위치 확인` 요청과 지도 갱신까지 확인했습니다. 보호자 화면에는 `A16 보는 중`, `아이 추가`, `보호자 초대 · 현재 1명`이 표시됐고 두 기기의 Firestore 권한 오류와 앱 충돌은 없었습니다.

첫 운영 시험에서는 콘솔에 구형 1:1 규칙이 남아 있어 가입 쓰기가 `PERMISSION_DENIED`로 거부됐습니다. 앱이 이 오류를 코드 만료로 잘못 안내하지 않도록, 유효한 초대 코드를 서버에서 다시 확인해 규칙 게시 누락과 실제 만료를 구분했습니다. N:N 규칙 게시본의 `createdByUid`, `schemaVersion`, 역할별 초대 검사를 확인한 뒤 새 번호로 다시 가입해 정상 통과했습니다.

실기기에서 추가로 세 가지 초기화 결함을 고쳤습니다. 최초 번호 발급이 실패하면 같은 화면에서 다시 시도할 수 있게 했고, 이미 선택된 자녀의 첫 콜백을 중복으로 오인해 관리 버튼이 계속 잠기던 문제를 바로잡았습니다. 장소 편집 지도도 선택된 자녀의 최근 위치에서 시작하도록 수정했습니다. 로컬 통합 테스트는 `-PfirebaseEmulator=true`인 디버그 빌드에서만 켜지고, 일반 디버그·릴리스 빌드는 운영 Firebase와 암호화 통신만 사용합니다.

실제 보호자 여러 명·자녀 여러 명의 동시 연결은 기기가 더 있을 때 추가 확인합니다. 이번 검증에서는 소리가 나지 않도록 벨소리·진동·무음·핸드폰 찾기 명령은 보내지 않았고, 자녀 폰의 위치 추적 알림이 `sound=null`인 것까지 확인했습니다.

### 지도 엔진 변경 기록

초기 카카오맵 SDK는 키가 준비되지 않아 OpenStreetMap으로 교체했지만, 최종적으로 보호자 경로 지도와 장소 지정 지도를 **네이버 지도 Android SDK**로 전환했습니다. 앱에는 Client Secret을 넣지 않고, 패키지 `com.kidcare.family`로 제한한 NCP Key ID만 `local.properties`를 통해 주입합니다.

주소 이름 변환은 지도 표시와 별개로 OpenStreetMap Nominatim을 계속 사용합니다. Nominatim의 사용 정책(초당 1회, 앱 식별자 표시, 결과 캐싱)은 기존 코드가 지킵니다.

### 네이버 지도·실시간 위치·적응형 경로 보정 (2026-08-13)

보호자 경로 지도와 장소 편집 지도를 네이버 Dynamic Map으로 통일했습니다. 인증값은 패키지명으로 제한된 NCP Key ID만 빌드할 때 주입하고, 모바일 앱에 넣으면 안 되는 Client Secret은 저장소와 APK 어디에도 사용하지 않습니다. 아이 마커는 앱 캐릭터로 바꾸고, 이동선은 흰색 테두리 위에 살구색·분홍색·보라색 그라데이션과 경유점을 더했습니다. 이동 카드별·전체 경로 표시를 각각 켜고 끌 수 있으며, 지도 아래 패널은 손잡이를 끌거나 버튼을 눌러 접고 펼칠 수 있습니다.

### 경로 중간이 사라지던 세 가지 원인 (2026-08-15)

"기기에 다 쌓고 부모가 부르면 전부 보여야 하는데 중간이 삭제된 느낌이고 선도 이상하다"는 보고를 받았습니다. 화면을 의심했는데 **셋 중 둘은 수집 쪽, 하나는 분배 쪽**이었고 그리기 자체는 멀쩡했습니다.

**첫째, 오차 30m를 넘는 후보를 경로에서 통째로 버리고 있었습니다.** 버스 안·번화가·실내는 GPS 오차가 30~50m로 몇 분씩 이어지는 것이 정상인데, 그 구간 내내 후보가 전부 거절되어 5분짜리 머무름 기준점만 남았습니다. 지도에서 정확히 "그 구간만 지워진" 모양이 됩니다. 상한을 상태 업로드와 같은 50m로 올렸습니다. 흔들림 억제는 두 점의 오차에 비례해 요구 변위를 키우는 `noiseRadius` 판정이 이미 맡고 있어서, 상한을 올려도 책상 위의 폰이 선을 그리지는 않습니다. 이동 판정기(`AdaptiveMovementDetector`)도 같은 30m 상한 때문에 거친 구간에서는 이동 확정까지 영영 못 올라갔으므로 함께 50m로 맞췄습니다.

**둘째, 활동 인식이 이동을 한 번 놓치면 스스로는 영영 돌아오지 못했습니다.** 가방 속 폰의 버스 이동처럼 활동 인식이 통째로 못 잡는 경우가 있는데, 전환 이벤트는 상태가 *바뀔 때만* 오기 때문에 한 번 놓치면 그날 내내 5분 주기에 갇힙니다. 이제 **정지 주기 한 번(5분) 사이에 좌표가 150m 넘게 옮겨졌으면 좌표 자체를 이동의 증거로** 삼아 5초 확인을 켭니다. 지오펜스 이탈을 이동 증거로 쓰던 것과 같은 원리입니다. 두 점의 오차가 최악으로 반대 방향이어도 100m(50m×2)를 넘을 수 없으므로 150m는 흔들림으로 만들 수 없는 거리입니다. 이동 확정 없이 5분이 지나면 정지 주기로 되돌려 배터리가 새지 않게 했습니다.

**셋째, 그리기가 이동 구간 창 밖의 점을 조용히 버렸습니다.** 경로선은 이동 카드 하나에 선 하나를 붙이려고 MOVE 구간의 `startAt..endAt`으로 점을 나눠 그렸는데, 그 사이에 떨어진 점(머무름 기준점, 구간 계산과 업로드의 미세한 어긋남, **마지막 이동 뒤에 들어온 최신 점**)이 어느 창에도 안 들어가 사라졌습니다. 부모가 가장 궁금해하는 최신 구간이 빠지는 것이 특히 나빴습니다. `RouteWindows`가 이웃한 두 구간 사이 공백의 **한가운데**에서 창을 갈라, 하루의 모든 시각이 정확히 한 창에 들어가도록 했습니다. 머무름 앞 절반은 앞 이동선에, 뒤 절반은 뒤 이동선에 붙어 선이 머무른 곳까지 이어집니다.

**"네이버 도로를 따라 그려달라"는 요청은 일부러 다르게 풀었습니다.** 네이버가 제공하는 것은 차량용 길찾기(A→B 최적 경로)라, 그걸 쓰면 아이가 실제로 간 길이 아니라 네이버가 계산한 길이 그려집니다. 골목·놀이터·횡단보도로 다니는 아이의 경로가 차도로 바뀌는 셈이라 자녀 안전 앱에서는 오히려 거짓말이 됩니다. 대신 위 세 수정으로 점이 촘촘히 채워지면 선이 저절로 실제 다닌 길을 따라갑니다 — 직선으로 건물을 가로지르던 것은 점이 듬성듬성해서였습니다.

단위 테스트는 146개에서 **158개**가 되었습니다(`RouteWindows` 5개, 변위 증거 5개, 거친 오차 구간 2개). 두 실기기에 릴리스 APK를 설치해 자녀 폰의 오늘 기록 복구(169점)와 업로드, 보호자 폰의 지도·마커·오차 원·이름·배터리 표시를 확인했습니다.

### 반경 100m 생활권에서 경로가 한 줄도 안 남던 문턱 여섯 (2026-08-17)

"아이가 반경 100m 안에서 모든 생활과 학원을 다니는데 GPS 기록이 없다. 집 앞 놀이터에 가도 이동 경로가 안 남고, 나도 모르는 사이에 저 멀리 텔레포트해 있다"는 보고를 받았습니다. 코드를 따라가 보니 **버그가 아니라 설계가 이 생활권과 맞지 않는 것**이었고, 문턱 여섯이 겹겹이 걷는 아이를 걸러내고 있었습니다.

먼저 실기기 로그가 진단을 확정해 줬습니다. 수집 주기가 **31초**로 15분 내내 고정이었는데, 이 값 자체가 증거입니다 — 활동 인식은 "이동 중"이라고 말하는데(정지였다면 5분) 좌표 판정기가 이동을 인정하지 않아 저주기로 내려앉아 있었다는 뜻입니다.

**① 이동 확정 문턱이 보행 속도로 도달 불가능했습니다.** 확인 창은 30초인데 아이 보행은 1.2m/s라 그 안에 36m를 갑니다. 그런데 오차 배수가 2.0이라 오차 15m만 돼도 42m, 20m면 57m를 요구했습니다. 즉 **뛰어야만 이동으로 인정**됐습니다. 배수를 1.0(=1시그마)으로, 최소 순이동을 30m에서 15m로 내렸습니다. 오탐이 늘지 않는 이유는 이 문턱이 혼자 판정하지 않기 때문입니다 — 표본 3개 이상, 10초 이상, 중간 지점도 문턱의 60%라는 '꾸준한 전진' 조건이 함께 걸려 있어 방향이 무작위인 흔들림은 연달아 만족하지 못합니다.

**② 같은 배수가 저주기 탈출에도 걸려 있었습니다.** 한번 저주기로 내려가면 30초 간격 두 점이 42~57m 벌어져야 복귀하는데, 이것도 뛰어야 나오는 값입니다. **걷는 아이는 하루 종일 저주기에 갇혔습니다.**

**③ 경로점 기록이 오차 반경을 요구했습니다.** `max(5m, hypot(오차1,오차2))`라 오차 20m면 연속 두 점이 28m 벌어져야 기록했는데, **아이가 5초 동안 걷는 거리는 6m**입니다. 즉 걸어서는 경로점이 한 개도 안 남았고, 속도 근거 갈래(정확도 15m 이하 + 속도오차 확보)가 통과할 때만 우연히 남았습니다. 3m 고정 문턱으로 바꿔 같은 좌표의 반복만 걸러냅니다. **설계 방침을 "수집은 넉넉히, 정리는 그릴 때"로 바꾼 것**이 이 변경의 본질입니다 — 버린 점은 영영 못 살리지만 남긴 점은 언제든 다듬을 수 있고, 흔들림 제거는 `RoutePathRefiner`가 이미 그리는 쪽에서 합니다. 저장 비용이 근거가 됩니다: CSV 한 줄 약 50바이트라 5초 간격으로 하루를 꽉 채워도 1MB 아래이고, 서버로는 어차피 하루 문서 하나만 갑니다. 제자리 흔들림을 막는 책임은 없어진 게 아니라 **상류의 이동 판정기로 옮겼습니다** — 판정기가 정지라고 하면 아래 필터는 한 줄도 기록하지 않습니다.

**④ 등록 장소 안에서는 판정기를 아예 안 돌렸습니다.** 집 반경 안의 놀이터에 다녀오는 동안이 정확히 그 상태였고, 수집 주기도 1분에 묶여 있었습니다. 작은 실내 움직임을 거르는 일은 판정기가 이미 하므로 하드코딩을 걷어냈습니다.

**⑤ 머무름 반경 100m가 하루를 한 덩어리로 만들었습니다.** 집·놀이터·학원이 모두 반경 100m 안이면 그 전부가 머무름 **하나**로 묶입니다. 그런데 지도의 경로선은 **이동(MOVE) 구간에만** 그려지므로, 이동 구간이 안 생기니 **선이 한 줄도 안 나왔습니다.** 40m로 내려 걸어서 1분 거리를 서로 다른 곳으로 가릅니다.

여기까지 고치고 다시 검토하다 **여섯 번째를 찾았습니다.** 위 다섯은 전부 "이동이 감지된 뒤"의 문턱이었는데, 집 앞 놀이터는 **감지가 시작조차 되지 않는** 문제였습니다. 네 갈래가 동시에 막혀 있었습니다 — 지오펜스는 놀이터가 집 반경 안이라 이탈이 없고, 활동 인식의 걷기 감지는 30초~2분 늦어 1분 산책이 이미 끝나 있고, 위치는 정지 판정 시 5분에 한 번만 들어오고, 좌표 변위 문턱은 150m인데 놀이터는 60m입니다. **좌표가 한 점도 없으면 변위로 판단할 재료조차 없습니다.**

**⑥ 정지 주기를 5분에서 1분으로, 변위 증거 문턱을 150m에서 50m로** 내렸습니다. 다만 변위 문턱은 오차에 연동했습니다(`max(50m, hypot×1.5)`). 고정 문턱만 쓰면 안 되는 이유가 있습니다 — 오차 40m짜리 두 점은 상한(50m) 안이라 통과하는데 그 변위 잡음은 표준편차가 57m라 **가만히 있어도 50m가 예사로 벌어집니다.** 그러면 서 있는 폰이 5초 주기를 계속 켜서 배터리만 태웁니다. 좌표가 좋을 때는 놀이터 거리를 잡고, 거칠 때는 애초에 구분할 수 없으므로 추측하지 않고 활동 인식과 지오펜스에 맡깁니다.

**실기기에서 확인한 것**: 서비스 시작 시 5초 확인으로 올라갔다가 실제 전진이 없자 35초 만에 저주기로 스스로 복귀해, 정지 중 배터리 보호가 살아 있음을 봤습니다. 재시작 복구(229점)와 업로드(230점)도 정상이었습니다. **아직 확인 못 한 것**은 실제로 걸어봤을 때 5초 모드로 올라가는지와 하루 배터리 소모입니다 — 둘 다 들고 나가야만 알 수 있습니다.

**네이버 길찾기처럼 도로에 붙여 그려달라는 요청은 일부러 다르게 풀었습니다.** 네이버가 주는 매끈한 선은 실제로 걸은 자취가 아니라 출발지→목적지를 미리 계산한 **예정 경로**입니다. 그걸 쓰면 아이가 실제로 간 골목·놀이터·단지 안 지름길이 차도로 바뀝니다. 애초에 아이가 어디 갈지 몰라서 이 앱이 있는 것이므로 목적지를 전제하는 계산 자체가 성립하지 않습니다. 대신 네이버가 매끈해 보이는 진짜 이유 중 가져올 수 있는 것 — **고빈도 샘플링** — 을 가져왔습니다. 점이 촘촘하면 선이 저절로 실제 다닌 길을 따라갑니다.

**남은 한계(정직하게)**: 집에서 놀이터까지 걸어가는 그 1분은 점이 1~2개로 얇을 수 있습니다. GPS가 거친 곳(실내·고층건물 사이)에서는 60m짜리 짧은 외출을 여전히 놓칠 수 있습니다. 그리고 집에서 40m 안에서만 노는 것은 점은 저장되지만 한 머무름으로 묶여 **선은 그려지지 않습니다.**

### 실외 보행 시험을 위한 양쪽 기기 설치 (2026-08-18)

다음 날 아이의 실제 이동을 보기 위해 문턱 여섯을 고친 릴리스 APK를 **두 대 모두**에 데이터 유지로 설치했습니다.

**보호자 기기까지 함께 올린 것이 이 작업의 핵심입니다.** 자녀 기기만 갱신하면 시험이 아무것도 보여주지 못합니다 — 머무름 반경 40m는 `SegmentBuilder`에 있고, 이 판정은 자녀 폰의 업로드(`TrailUploader`)뿐 아니라 **보호자 폰이 지도를 그릴 때**(`MapTimelineFragment`)도 다시 돕니다. 보호자 앱이 옛 100m 반경을 쓰면 아이 폰이 점을 아무리 촘촘히 쌓아도 화면에서 그 전부가 머무름 하나로 다시 뭉치고, 경로선은 이동 구간에만 그려지므로 결과는 고치기 전과 똑같이 "선 없음"입니다. 8월 16일 인수인계 1번이 짚어둔 자리였습니다.

설치 뒤 자녀 기기(갤럭시 S24+)에서 확인한 것: 가족 문서와 지금까지 쌓인 경로가 그대로 남아 있고(`install -r`), 수집 서비스가 포그라운드로 살아 있으며, 새 프로세스가 `수집 주기 변경: 이동 확인 5초`를 찍어 새 코드가 실제로 도는 것을 봤습니다. 배터리 최적화 예외와 백그라운드 위치 권한도 켜져 있습니다.

같은 로그에서 좌표가 전부 `REJECT_INACCURATE`로 거절되고 있었는데 **이것은 고장이 아닙니다.** 심야 실내라 오차가 100~200m로 나오고 상한은 50m입니다. 실내에서 점이 안 쌓이는 것은 이 설계가 의도한 동작이며, 다음 날 밖으로 나가면 오차가 한 자리수~15m로 떨어집니다. 앱 로그를 처음 보는 사람이 이 줄만 보고 버그로 오해하기 쉬워 적어 둡니다.

**아직 확인 못 한 것은 그대로입니다** — 실제로 걸었을 때 5초 모드로 올라가는지, 60m 놀이터 외출이 이동으로 시작되는지, 하루 배터리가 얼마나 드는지. 셋 다 아이가 들고 나가야만 알 수 있습니다.

### 공휴일엔 예약을 쉬어요 — 요일로는 절대 못 적는 것 (2026-08-18)

부모가 예약 규칙을 쓰는 방식은 "평일 몇 시엔 진동, 몇 시엔 무음"입니다. 그런데 **공휴일은 요일이 아닙니다.** 설날·추석·부처님오신날은 음력이라 해마다 자리를 옮기고, 대체공휴일은 그 해 요일 배치에 따라 생겼다 없어집니다. 부모가 미리 찍어 둘 수 있는 값이 아니라 해마다 다시 계산해야 하는 값이라, 요일 일곱 칸으로는 표현할 방법이 없습니다.

그래서 규칙(부모가 정한 것)과 달력(해마다 달라지는 것)을 섞지 않았습니다. 규칙에는 공휴일 칸을 만들지 않고, 예약 전체에 걸리는 스위치 하나를 목록 **위**에 뒀습니다. 이건 규칙이 아니라 달력이기 때문입니다 — 목록 안에 한 줄로 넣으면 다른 규칙과 같은 무게로 읽혀서, 켜고 끄면 무엇이 달라지는지가 흐려집니다.

**날짜 표를 코드에 적지 않은 것이 이 작업의 핵심 결정입니다.** 몇 해치를 적어 두면 그 해가 지나는 순간 앱이 조용히 틀립니다 — 부모는 공휴일에 쉬는 줄 알고 있는데 아이 폰만 평일처럼 무음이 되고, 아무 오류도 안 납니다. 대신 안드로이드가 기기에 들고 있는 ICU 달력(`android.icu.util.ChineseCalendar`, API 24+)으로 음력을 환산합니다. 천문 계산이라 표를 갱신할 일이 없고 새 의존성도 없습니다.

대체공휴일은 규칙으로 계산합니다. 설날·추석 연휴는 **일요일**과 겹칠 때만(토요일은 아닙니다), 어린이날은 주말이나 다른 공휴일과 겹칠 때, 삼일절·광복절·개천절·한글날·부처님오신날·성탄절은 주말과 겹칠 때 하루가 붙습니다. 신정과 현충일은 대체공휴일이 없습니다. 이 규칙이 맞는지는 **실제로 있었던 해로 검산했습니다** — 2025년은 대체공휴일 세 개가 서로 다른 이유로 생긴 해(삼일절 토요일, 어린이날이 부처님오신날과 겹침, 추석 연휴가 일요일을 뭄)라 세 갈래를 한 해로 전부 확인할 수 있습니다. 2026년도 함께 넣었습니다.

판정 자체는 요일과 같은 자리에 뒀습니다: **공휴일에는 어떤 규칙도 시작하지 않는다.** 시작일 기준이라는 점이 요일과 똑같습니다 — "평일 22:00~07:00"이 금요일 밤에 시작해 토요일 새벽까지 이어지듯, 목요일 밤에 시작한 규칙은 금요일이 공휴일이어도 그 아침까지는 이어집니다. 부모가 정한 것은 "언제 시작하는가"이므로 기준을 한 곳에만 둡니다.

**검산할 자리를 화면에 뒀습니다.** 음력 환산이 틀리면 증상 없이 엉뚱한 날에 쉬므로, 스위치를 켜면 그 아래에 "다음 쉬는 날은 9월 24일 추석 연휴이에요"라고 적습니다. 부모가 달력과 눈으로 맞춰볼 수 있는 유일한 지점입니다. 같은 값이 로그에도 한 번 찍힙니다.

한계 하나는 알고 씁니다: 우리 음력은 한국 시각(UTC+9) 기준이고 ICU 의 계산은 중국 시각(UTC+8) 기준이라, 삭이 자정 언저리에 걸리는 드문 해에는 하루가 어긋날 수 있습니다. 그런 해의 결과는 "쉬는 날 하루가 예약을 안 쉰다" 정도라, 표를 손으로 관리하다 통째로 틀리는 쪽보다 낫다고 봤습니다.

설정은 기존 `settings/ringer` 문서에 필드 하나로 얹었습니다 — **보안 규칙을 새로 게시할 필요가 없습니다.** 대신 이 문서를 두 화면(관리 탭의 잠금, 예약 탭의 공휴일)이 함께 쓰게 되므로, 통째로 덮어쓰던 저장을 **필드별 병합**으로 바꿨습니다. 안 그러면 한쪽 스위치를 누를 때마다 다른 쪽이 기본값으로 되돌아갑니다.

### 예약 탭 재디자인 — 하루 띠 (2026-08-18)

"다른 메뉴는 괜찮은데 예약만 안 예쁘다"는 지적을 받았습니다. 보니 이 탭만 색이 없었습니다 — 다른 탭은 연한 색 카드와 그림으로 말하는데, 예약은 흰 바탕에 글자와 외곽선 버튼뿐이었습니다.

세 가지를 더했습니다.

**소리 모드 스티커.** 규칙마다 왼쪽에 동그란 스티커를 붙여 벨소리는 살구빛, 진동은 라벤더, 무음은 풀빛으로 나눴습니다. 색만 쓰지 않고 그림도 함께 넣은 이유는 색을 못 가리는 눈에는 셋이 같은 동그라미가 되기 때문입니다. 세 색이 스티커 바탕·그림·아래 띠 세 자리에 쓰이므로 `ScheduleText.modeLook` 한 곳에 모았습니다 — 세 곳에 따로 적으면 하나를 바꿀 때 반드시 하나를 빠뜨립니다.

**하루 띠.** 이 화면이 다루는 것은 결국 "하루의 어디"입니다. 글자만 있으면 `22:00 ~ 다음 날 07:00`을 머릿속에서 시계로 옮겨야 하는데, 자정부터 자정까지를 한 줄로 펴 놓고 규칙이 도는 동안만 색을 채우면 그 일을 화면이 대신합니다. 조각이 셋인 이유가 자정 넘김입니다 — 낮 규칙은 가운데가 차고 **밤 규칙은 양 끝이 찹니다.** 규칙이 여러 개 쌓이면 하루가 어떻게 나뉘어 있는지가 목록만 훑어도 보입니다.

**소리 모드 버튼에 그림.** 편집 화면의 벨소리·진동·무음 버튼이 글자만 있어서 셋이 똑같아 보였습니다. 위쪽에 그림을 얹어 목록의 스티커와 같은 그림을 쓰게 했습니다 — 고를 때 본 그림이 목록에 그대로 나옵니다.

### 14개 언어 — 원본은 한 벌, 기본값은 영어 (2026-08-18)

해외에서도 쓸 수 있게 화면 문장 **337개를 14개 언어**로 옮겼습니다. 언어 목록과 도구는 [공용 저장소](https://github.com/Yongminlee2/common)의 `i18n/` 을 그대로 썼습니다 — 이 집 앱들이 스택마다 흩어져 있어 번역 원본은 한 벌만 두고 거기서 뽑아 쓰는 방식입니다.

**`strings.xml` 을 손으로 쓰지 않습니다.** 원본은 `i18n/<언어>.json` 이고 `gen.py` 가 `res/values-*/strings.xml` 을 만듭니다. 손으로 쓰면 `'` `"` `&` `%` 이스케이프를 빼먹는데, 그러면 **빌드는 통과하고 화면에서만 깨집니다.** 고칠 때는 JSON 을 고치고 다시 뽑습니다.

**기본값(`res/values/`)이 영어이고 한국어는 `values-ko/` 로 옮겼습니다.** 지원하지 않는 언어의 기기는 전부 기본값으로 떨어지므로, 한국어를 기본에 두면 그리스 사용자가 한글을 봅니다.

디렉터리 이름의 함정 둘을 그대로 밟지 않도록 적어 둡니다. **인도네시아어는 `values-in`** 입니다(자바 레거시 코드 — 태그는 `id`인데 폴더만 다릅니다). **번체 중국어는 `values-zh-rTW` 와 `values-zh-rHK` 둘 다** 둡니다. 안 그러면 홍콩 기기가 간체로 떨어집니다.

숫자 자리(`%1$s`)는 그대로 뒀습니다. 공용 도구는 스택 중립을 위해 `{}` 를 권하지만 이 앱은 코틀린 전용이고 `getString(id, a, b)` 로 이미 위치 인자를 쓰고 있어, 바꾸면 얻는 것 없이 호출부를 전부 건드려야 합니다. `audit.py` 의 자리 개수 검사는 `%1$s` 도 셉니다.

**번역이 끝나면 `audit.py` 를 돌립니다.** 이 검사가 잡는 것은 사람 눈에 잘 안 보이는 종류입니다 — 자리 개수가 어긋나 앱이 죽는 것, 옮기다 만 한글, 그리고 일본어·중국어·태국어에 들어간 낱말 사이 빈칸. 실제로 일본어에서 `リアルタイム位置  接続中…` 이 걸렸습니다. 한국어 원문의 두 칸 띄어쓰기가 그대로 넘어간 것인데, 빈칸으로 낱말을 나누지 않는 말에서는 조각을 늘어놓은 것처럼 보입니다. 최종 결과는 **확정 0건**입니다.

**언어 선택은 두 갈래로 둡니다.** 안드로이드 13+ 는 매니페스트의 `localeConfig` 로 시스템 설정에 앱 언어 칸이 생기고, 그 아래 버전에는 그 칸이 없으므로 화면 위쪽 지구본 버튼을 뒀습니다. `minSdk` 가 26이라 이게 없으면 절반쯤 되는 기기에서 언어를 바꿀 길이 아예 사라집니다. 아이 폰에도 따로 뒀습니다 — 부모와 아이가 같은 나라 말을 쓴다는 보장이 없습니다.

레이아웃은 **러시아어와 태국어로 실기기 확인**했습니다. 러시아어는 글자가 제일 길어 칸을 넘치는지 보고, 태국어는 낱말을 띄어 쓰지 않아 줄바꿈이 이상한 자리에서 끊기는지 봅니다. 둘 다 잘리는 곳 없이 그려졌습니다.

**공휴일 이름은 한국 공휴일 그대로 옮겼습니다.** 계산이 한국 달력이라 이름도 그것을 가리켜야 합니다 — 추석을 그 나라의 명절 이름으로 바꾸면 날짜와 뜻이 어긋납니다.

### 규칙이 끝나도 안 돌아오던 문제, 그리고 인터넷 상태 (2026-08-18)

"예약이 몇 시부터 몇 시까지인데, 끝난 시각에 원래대로 안 돌아가고 쭉 간다"는 보고를 받았습니다. 코드를 보니 **버그가 아니라 빠진 개념**이었습니다.

`RingerController.desiredMode` 는 걸린 규칙이 없으면 `null` 을 돌려주고, `ScheduleApplier.applyNow` 는 `null` 이면 **아무것도 하지 않습니다.** 그래서 "평일 밤 무음"을 걸면 아침 7시가 지나도 무음인 채로 남았습니다. 규칙은 **언제 시작하는지만** 말할 뿐 끝난 뒤 무엇으로 돌아갈지는 말하지 않기 때문입니다.

돌아갈 자리를 한 곳에 두는 것으로 풀었습니다 — 예약 탭 맨 위의 **"예약이 없는 시간에는"** 카드입니다. 그대로 두기·벨소리·진동·무음 중 하나를 고르면 규칙이 끝날 때 거기로 돌아갑니다. 기본값은 `그대로 두기`라 **정하지 않으면 예전과 똑같이 동작합니다** — 업데이트만으로 이미 쓰던 사람의 폰이 말없이 달라지면 안 됩니다.

이 카드를 공휴일 스위치보다 **위**에 둔 이유가 있습니다. 기본 모드는 "예약이 없을 때"를 정하는 바탕이고, 공휴일 스위치는 그 바탕 위에서 규칙을 쉬게 하는 것입니다. 바탕이 먼저 읽혀야 합니다.

설정은 기존 `settings/ringer` 문서에 필드로 얹었습니다 — **보안 규칙을 새로 게시할 필요가 없습니다.**

**관리 탭에 인터넷 연결 상태를 더했습니다.** 와이파이로 붙었는지, 데이터로 붙었는지, 아예 못 붙었는지와 와이파이 스위치 상태를 보여줍니다. 두 줄로 나눈 이유는 둘이 다른 것을 말하기 때문입니다 — 와이파이 스위치가 켜져 있어도 공유기가 인터넷에 못 나가면 첫 줄은 "연결돼 있지 않아요"가 됩니다. 부모가 "왜 위치가 안 와요"를 풀 때 필요한 것이 그 구분입니다.

**끄고 켜기는 만들지 않았습니다. 만들 수 없습니다.** 안드로이드 10부터 `WifiManager.setWifiEnabled` 는 서드파티 앱에 항상 실패를 돌려주고, 모바일 데이터는 그보다 더 오래전부터 막혀 있습니다. 유일한 우회로인 기기 소유자(Device Owner) 등록은 **아이 폰을 초기화해야** 하는데, 그건 이미 안 하기로 정한 길입니다(6단계 계획서). 화면 안에 그 사실을 한 줄로 적어 뒀습니다 — 안 적으면 "왜 스위치가 없지"가 계속 질문으로 돌아옵니다.

### 네 탭을 한 격자에 앉히고, 탭마다 눈이 갈 곳을 하나씩 (2026-08-18)

"지도 탭은 괜찮은데 알림·관리·예약·장소 탭 디자인이 별로다"는 지적을 받고, 눈으로 보기 전에 **레이아웃 파일에서 값을 세어 봤습니다.** 원인이 숫자로 나왔습니다.

| | 지도 | 알림 | 관리 | 예약 | 장소 |
|---|---|---|---|---|---|
| 카드 개수 | 6 | 2 | 4 | 4 | **0** |
| 화면 좌우 | 14dp | 20dp | 20dp | 20dp | 20dp |
| 목록 줄 좌우 | 5dp | 12dp | — | 14dp | 12dp |
| 화면 제목 | 없음 | TitleLarge | HeadlineSmall | HeadlineSmall | HeadlineSmall |

**머리말은 20dp 안쪽인데 그 아래 카드는 12~14dp 안쪽이었습니다.** 모든 탭에서 왼쪽 선이 6~8dp 어긋나 있었고, 탭을 바꾸면 그 어긋남의 크기까지 바뀌었습니다. 화면 제목은 알림 탭만 크기가 달라서, 탭을 넘길 때 제목 글씨가 커졌다 작아졌다 했습니다.

**꾸밈이 부족한 게 아니라 규칙이 없는 것이 문제였습니다.** 색도 팔레트가 있고 마스코트도 있는데, 그것들을 놓는 값을 파일마다 손대는 사람이 그때그때 정했습니다. 그래서 값을 먼저 한 곳에 못박았습니다 — `res/values/dimens.xml` 이 그 정본표입니다. 새 화면은 거기 있는 값만 씁니다.

지도 탭은 **일부러 예외로 뒀습니다.** 그 화면은 지도 위에 카드가 떠 있는 구조라 좌우 여백의 뜻이 다르고, 지금 모양이 좋다는 평가를 받았습니다.

통일 다음에 탭마다 눈이 갈 곳을 하나씩 뒀습니다. 순서가 중요합니다 — 반대로 하면 예쁜 조각이 또 삐뚤빼뚤 놓입니다.

- **장소**: 카드가 하나도 없어 제일 심심했습니다. 예약 줄과 같은 뼈대의 카드로 바꾸고, 왼쪽 동그라미에 **장소 이름의 첫 글자**를 넣었습니다. 핀 그림 하나를 다섯 줄에 반복하는 것보다 훨씬 빨리 구분됩니다 — 목록을 훑는 부모가 찾는 것은 "장소"가 아니라 "학교"입니다. 색은 문서 ID 로 정해서 순서가 바뀌어도 같은 장소는 같은 색을 지킵니다(자리로 정하면 하나 지울 때 아래가 전부 밀립니다).
- **알림**: 여섯 종류가 전부 같은 하늘색 동그라미였습니다. 뜻에 맞춰 색을 갈랐습니다 — 도착은 풀빛, 나섬은 살구빛, 배터리·권한·신호 문제는 자두빛.
- **예약·관리**: 앞서 만든 소리 모드 스티커와 하루 띠, 상태 카드가 그 자리입니다.

### 줄은 맞췄는데 헐렁했다 — 밀도 (2026-08-18)

격자를 맞추고 나서 "이제 됐다"고 했는데 "여전히 별로다, 버튼이 쓸데없이 크고 예약 탭에 규칙이 세 개밖에 안 보인다"는 지적을 받았습니다. **지적이 맞았고, 제가 축 하나를 통째로 빼먹고 있었습니다.** 여백을 맞추는 일만 했지 *한 화면에 얼마나 담기는가*는 한 번도 재지 않았습니다.

재보니 숫자가 분명했습니다. 예약 탭에서 **진짜 내용인 규칙이 화면의 27%**였습니다.

| | 높이 | 무엇 |
|---|---|---|
| 제목 + 부제 | 300px | 글씨만 |
| 기본값 카드 | 312px | 설정 하나 |
| 공휴일 카드 | 168px | 설정 하나 |
| 규칙 한 줄 | 216px | ← 이게 내용 |
| 추가 버튼 | 132px | 버튼 하나 |

원칙 셋을 정하고 넷 다 같은 원칙으로 밀었습니다.

**① 같은 말을 두 번 하지 않는다.** 규칙 줄의 `· 진동` 을 지웠습니다 — 왼쪽 스티커가 그림과 색으로 이미 말하고 있어서 같은 뜻이 두 번 나왔고, 긴 요일 조합에서는 그 때문에 두 줄로 접혔습니다. 화면 제목 넷도 걷어냈습니다: 아래 탭이 늘 보이면서 "알림·관리·예약·장소"라고 말하는데 그 바로 밑에 같은 뜻을 한 번 더 크게 적고 있었습니다. 제목 하나가 위아래 여백까지 **110px**, 규칙 반 줄 자리입니다.

**② 설명은 한 번 읽으면 끝이다.** 부제 넉 줄과 기본값 카드의 설명 줄을 뺐습니다. 문구 자체는 빈 화면이 그대로 쓰므로 지우지 않았습니다 — 처음 온 사람에게 필요한 말이 매번 자리를 차지할 이유는 없습니다.

**③ 여백은 손가락이 닿는 데만 넉넉히.** 추가 버튼 56→48dp(손가락은 48dp면 충분합니다), 위아래 여백 24→16dp, 스티커 44→40dp, 하루 띠 7→4dp.

실기기에서 잰 결과입니다.

| | 처음 | 1차 | 2차 |
|---|---|---|---|
| 첫 규칙 시작 | y=1060 | y=880 | y≈700 |
| 줄 간격 | 245px | 225px | ≈205px |
| 한 화면 규칙 | **3개** | 4개 | **5~6개** |

화면에서 사라진 머리말·부제 열쇠 일곱 개는 14개 언어 원본에서도 지웠습니다. 안 지우면 다음 사람이 "이 문구 어디에 나오지"를 찾다가 없는 화면을 뒤집니다.

**마스코트를 잘못 쓴 것도 이때 잡혔습니다.** 빈 화면에 그림을 넣으면서 `ic_mascot`(납작한 벡터)을 썼는데, 이 앱의 진짜 마스코트는 `mascot_3d` 입니다 — 아이 폰 화면·페어링·역할 선택·지도 탭·지도 마커까지 **아홉 군데**가 그것을 쓰고 있었고 제가 만든 두 곳만 다른 얼굴이었습니다. 새 화면에 그림을 넣을 때는 먼저 **이미 어느 그림을 쓰고 있는지 세어 보는 것**이 순서입니다.

### 방해금지가 켜지면 소리 상태가 거짓말을 하던 문제 (2026-08-18)

"벨소리로 설정돼 있는데도 무음으로 가져온다, 방해금지면 방해금지라는 걸 알 수 있으면 좋겠다"는 보고를 받았습니다. 보고가 정확했고, 원인은 안드로이드 쪽에 있습니다.

**방해금지(DND)가 켜지면 `AudioManager.getRingerMode()` 는 무조건 `SILENT` 를 돌려줍니다.** 아이가 벨소리로 맞춰 놨어도 그렇습니다. 그래서 그 값만 올리면 부모 화면에 "무음"이 뜨고, 부모는 아이가 소리를 바꾼 줄 압니다. 실제로는 방해금지가 덮고 있을 뿐입니다.

실기기에서 그 동작을 눈으로 확인했습니다. 방해금지를 켜자 `dumpsys audio` 의 음소거 스트림이 `0x126` 에서 `0x136` 으로 늘었습니다 — **알람 스트림까지 음소거에 들어갑니다.** 시스템이 소리 상태를 통째로 덮는다는 뜻입니다.

그래서 방해금지 상태를 **소리 모드와 따로** 올립니다. 두 값을 함께 봐야 화면이 거짓말을 하지 않습니다. 방해금지가 켜져 있으면 관리 탭의 소리 상태가 "방해금지 모드"로 바뀌고, 그 아래 한 줄이 왜 그런지 말해 줍니다.

읽는 길은 두 갈래로 뒀습니다. 먼저 공개 API(`NotificationManager.getCurrentInterruptionFilter`)를 쓰고 — 이 앱은 소리 변경 때문에 이미 방해금지 접근 권한을 받아 둡니다 — 그것이 `UNKNOWN` 이면 시스템 설정값 `zen_mode` 를 직접 읽습니다. 실기기에서 `zen_mode` 가 권한 없이 `0 → 1 → 0` 으로 읽히는 것을 확인했으므로, 아직 권한을 안 준 폰에서도 답이 나옵니다.

소리 모드만 바꾸는 갱신 경로(`reportRingerMode`)에도 방해금지를 함께 실었습니다. 한쪽만 새로 쓰면 부모 화면이 **옛 방해금지 값으로 새 소리 모드를 해석해** 또 어긋납니다.

### 예약 추가 화면을 한 격자에 다시 앉힘 (2026-08-18)

"아이콘이랑 글자 크기·위치가 안 맞고 삐뚤삐뚤하다, 글씨는 쓸데없이 크다"는 지적을 받고 화면을 픽셀로 재봤습니다. 지적이 맞았고 원인은 셋이었습니다.

**왼쪽 정렬선이 다섯 개였습니다.** 머리말 글자 155px, 요일 48, 시각 42, 모드 50, 취소 214. 머리말마다 붙인 동그란 스티커가 글자를 38dp 밀어내 같은 화면에 선을 두 개 만들고 있었고, 낱개 버튼마다 준 좌우 여백이 첫 칸을 안쪽으로 밀었고, 취소는 글자 버튼이라 자기 여백만큼 더 들어가 있었습니다.

고친 방법: 머리말 스티커를 걷어내고(그림은 이미 모드 버튼 안에 있어서 중복이었습니다), 여백은 칸 **사이**에만 주고, 취소를 외곽선 버튼으로 바꿔 저장과 같은 격자에 앉혔습니다. 지금은 모든 줄이 **왼쪽 42px·오른쪽 1037px** 한 선에서 시작하고 끝납니다.

**높이가 32·52·66·86 이었습니다.** 4의 배수 격자(44·56·72·52)로 맞췄습니다.

## 아이가 앱을 강제 종료하면 — 막을 수 없고, 대신 부모에게 알립니다

아이 폰에서 **설정 → 애플리케이션 → 우리아이 지킴이 → 강제 중지**를 누르면 이 앱은 멈춥니다. 권한도 비밀번호도 필요 없습니다.

그러면 안드로이드가 앱을 "stopped" 상태로 두는데, 그 상태에서는 **부팅 신호(`BOOT_COMPLETED`)가 배달되지 않고 걸어둔 알람이 전부 취소됩니다.** 원격 명령 수신, 되돌리기, 시간대 예약, 그리고 **위치 추적까지** 한꺼번에 멎습니다. 폰을 껐다 켜도 살아나지 않습니다.

**되살리는 방법은 하나입니다 — 아이 폰에서 앱을 한 번 열면 됩니다.** 열기만 하면 서비스가 다시 뜨고 알람도 다시 걸립니다.

**막지 않기로 했습니다.** 이걸 막으려면 기기관리자(Device Admin) 권한이 필요한데, 그건 오작동하면 폰 초기화까지 얽히는 권한이라 아이 폰에 걸어두기엔 위험이 이득보다 큽니다(위 "의도적으로 안 만든 것" 참고). 사이드로드로 깔린 일반 앱이 자기 강제 종료를 막는 방법은 안드로이드에 없습니다.

**대신 부모에게 말합니다.** 예전에는 부모가 명령을 하나 보내고 60초를 기다려 "애기폰이 응답하지 않아요"를 볼 때까지, 그것도 관리 탭에서만 알 수 있었습니다. 지금은 보호자 화면 맨 위에 배너가 뜹니다 — 지도 탭이든 관리 탭이든 같은 자리입니다.

```
⚠️ 오후 2:31에 보낸 요청에 애기폰이 아직 대답하지 않았어요
아이 폰에서 '우리아이 지킴이' 앱을 한 번 열어주세요. 그러면 다시 이어져요.
```

판정은 **"물어봤는데 대답이 없는가"**입니다(`logic/DisconnectRule`). 세 조건을 전부 만족해야 뜹니다 — ① 한 번이라도 물어본 적이 있고, ② 그 마지막 물음 뒤로 대답이 없고, ③ 그 물음이 **30분** 넘게 묵었을 때.

"아이 폰에서 30분 넘게 아무 신호가 없으면"이 **아닙니다.** 아이 폰은 이제 주기적으로 아무것도 올리지 않으므로(위 "무료 한도" 절), 침묵 자체는 정상 상태입니다. 물어본 적 없는 폰은 대답하지 않은 것이 아닙니다 — 페어링만 끝내고 '지금 위치 확인'을 한 번도 안 눌러 본 부모에게 "연결이 끊겼어요"라고 말하는 것은 거짓말입니다.

30분인 이유는 한 번의 무응답(터널, 절전 낮잠)으로 헛경보를 내지 않기 위해서입니다. 5분이나 10분으로 잡으면 멀쩡한 폰에 헛경보가 나고, 헛경보가 몇 번 나면 부모는 진짜로 끊긴 날에도 이 문구를 안 읽습니다. 아이 폰이 대답하면 배너는 저절로 사라집니다 — **실패(`failed`)도 대답으로 칩니다.** 실패 이유를 적어 보낼 수 있었다는 것 자체가 살아 있다는 뜻이니까요.

판정 재료는 **부모 폰 안에만** 있습니다(언제 물었고 언제 대답이 왔는가, 두 값). 서버에 두면 그것을 읽고 쓰는 것 자체가 무료 한도를 먹고, 두 값을 적는 것도 빼는 것도 같은 폰이라 폰 시계가 어긋나 있어도 차이는 정확합니다.

### 실기기 검증 (갤럭시 A16 · 안드로이드 16)

1~3단계 전체를 실제 폰에서 확인했습니다.

- 설치·역할 선택·익명 로그인
- 보호자 가족 생성과 초대 코드 발급 (3회, 매번 정상)
- **자녀 페어링** — 배포된 보안 규칙을 실제로 통과
- 권한 안내 → 자녀 홈 → 포그라운드 서비스 기동, 상시 알림 유지
- 위치 수집·필터 동작, 구간 재계산
- **지도(타일·마커·경로선)와 타임라인**
- 날짜 이동, 오늘 기준 다음 날 버튼 비활성
- "역할 다시 고르기"로 저장값이 완전히 초기화되는지

초기 검증 당시에는 폰이 한 대라 **아이 폰 역할을 PC 스크립트로 대신했습니다**. 이후 2026-08-12에 갤럭시 탭 S7과 A16 두 대를 운영 Firebase에 새로 연결해 릴리스 APK의 실제 보호자·자녀 통신까지 확인했습니다.

**실기기가 아니면 못 잡았을 문제 3개**

1. 오류가 **영어 원문**(`PERMISSION_DENIED: Missing or insufficient permissions.`)으로 떴습니다. 부모가 이걸 보고 할 수 있는 게 없습니다 → 한국어 안내로 교체.
2. **실패했다면서 로딩 표시가 계속 돌았습니다.** 이건 전수 리뷰가 *"오류 문구가 바로 위에 있으니 괜찮다"* 며 넘겼던 항목인데, 실제 화면에서는 스피너가 글자보다 눈에 잘 띄어 "아직 하는 중"으로 읽혔습니다. **코드만 읽고 UI를 판정하면 안 된다**는 걸 확인한 사례라 판단을 뒤집고 고쳤습니다.
3. **Firestore 복합 색인이 없으면 타임라인이 영원히 빕니다.** 지도는 멀쩡하고 목록만 비어서 "데이터가 없나 보다"로 보입니다. 예외 객체를 통째로 로그에 남기도록 해둔 덕에 생성 링크를 로그에서 건질 수 있었습니다. (이 색인은 지금 필요 없습니다 — 타임라인이 쿼리 대신 하루 문서 한 건을 ID로 곧장 읽게 바뀌었습니다.)

### 배포용 빌드 확인 (6단계)

코드 축소를 켠 APK를 아이 폰에 실제로 깔아 확인했습니다. 14.2MB → **3.7MB**.

- 자녀 홈 화면이 정상적으로 그려지고, `versionCode = 6`, 디버그 플래그 없음
- 릴리스 서명이 다르면 기존 설치에 덮이지 않으므로(`INSTALL_FAILED_UPDATE_INCOMPATIBLE`), 같은 APK를 디버그 키로 다시 서명해 깔았습니다 — 서명 외 811개 항목이 바이트까지 동일함을 확인했습니다

**2026-08-12 후속 확인**: 운영용 축소 릴리스 APK에서 보호자 탭 다섯 개, 자녀 선택, 이동 기록 접기·펼치기, 장소 편집 지도의 시작 위치와 `지금 위치 확인` 응답을 확인했습니다. 소리 변경·핸드폰 찾기·원격 알람은 조용한 환경에서 시험해야 해 버튼 상태만 확인했습니다.

## 설정하고 빌드하기

자세한 절차는 [`docs/setup.md`](docs/setup.md)에 있습니다. 요약하면:

1. **Firebase 프로젝트 생성** → 안드로이드 앱 추가(패키지 `com.kidcare.family`) → `google-services.json`을 `app/`에 저장
2. **익명 인증** 켜기, **Firestore** 생성(`asia-northeast3`, 프로덕션 모드)
3. **보안 규칙·색인 게시** — Firebase CLI에서 `firebase deploy --only firestore` 실행. `firebase.json`이 `firestore.rules`와 `firestore.indexes.json`을 함께 게시합니다
4. **복합 색인 확인** — `commands`(`state` + `createdAt`)와 `events`(`childUid` + `at`) 두 개가 필요합니다
5. 빌드

```bash
./gradlew.bat :app:assembleDebug
```

무료 Spark 요금제로 충분합니다. 카드 등록이 필요 없습니다. **가족 하나가 쓰는 동안에는** 한도의 한참 아래입니다 — 여러 가족으로 늘리려 할 때의 계산은 [`docs/known-issues.md`](docs/known-issues.md) 12·14번에 있습니다.

배포용(서명 + 코드 축소) 빌드는 키스토어가 필요합니다. 절차는 [`docs/setup.md`](docs/setup.md)의 "릴리스 서명" 절에 있습니다.

| `values/colors.xml`의 `mascot_*` | `values-night/`에 **넣지 말 것** | 밤 모드에서 캐릭터 얼굴이 배경과 같이 어두워져 눈만 뜬 검은 덩어리가 됩니다 |
| `targetSdk` | 낮추지 말 것 | WiFi 제어 같은 옛 API가 살아나는 대신 위치 수집이 망가집니다. 앱의 본체를 부수는 거래입니다 |

### 코드 작성 규칙

- **`CancellationException`은 어떤 일반 `catch`·`runCatching`보다 먼저 다시 던집니다.** 이 저장소에서 같은 사고를 아홉 번 고쳤습니다.
- 프래그먼트는 `onDestroyView`에서 리스너를 전부 해제하고 바인딩을 `null`로 둡니다. 늦게 오는 콜백은 바인딩 `null` 검사로 막습니다.
- **장소 지도를 코드로 옮길 때는 되돌아오는 카메라 이벤트를 막으세요.** 프로그램이 카메라를 옮겨도 카메라 유휴 콜백이 오므로, 그 리스너가 "지도 중심 = 사용자가 고른 좌표"로 상태를 되받아쓰면 아직 준비되지 않은 중심 좌표가 저장될 수 있습니다. `PlaceFragment.suppressMapCallbacks`가 그 방어입니다.
- 사용자에게 보이는 문구는 전부 `strings.xml`, 한국어. 실패 문구는 `core/ErrorText.errorMessage(...)`를 거칩니다 — SDK 원문이 부모에게 보이면 안 됩니다.
- 주석은 한국어로 **왜** 를 적습니다. 집필 기준은 `core/AuthGateway.kt`.
- 커밋 메시지는 한국어로 작성합니다.

### 함께 고쳐야 하는 짝

한쪽만 바꾸면 컴파일은 되는데 조용히 안 도는 자리들입니다.

- **새 명령 타입** → `core/model/Documents.kt`의 `CommandType` + `child/CommandHandler.kt`의 `when` + 보내는 화면. 셋 다.
- **새 이벤트 타입** → `EventType` + `guardian/AlertAdapter.kt`의 `when`. 상수를 참조하면 컴파일러가 잡아줍니다(리터럴 쓰지 마세요).
- **장소를 바꾸는 경로** → 반드시 `guardian/PlaceFragment.kt`의 `writeThenNotify`를 지나야 합니다. 그 함수가 쓰기 뒤에 `SYNC_RULES`를 보냅니다. 안 지나면 아이 폰이 지오펜스를 다시 걸지 않아, **지운 장소의 알림이 계속 울립니다.**
- **`firestore.rules` 또는 `firestore.indexes.json`을 고쳤으면** → `firebase deploy --only firestore`로 **다시 게시**해야 합니다. 로컬 파일만 바꾸면 아무 효과가 없습니다. 0.7 N:N 전환 순서는 **규칙·색인 먼저, APK 나중**입니다. 새 규칙은 0.6 자녀 코드 가입도 허용하므로 이 순서가 안전합니다.

### 사람이 직접 해야 하는 것 (코드로 대신 못 함)

1. **보안 규칙·색인 게시** — `firebase deploy --only firestore`. 콘솔에서 직접 할 경우 `firestore.rules` 전체와 `firestore.indexes.json`의 두 색인을 모두 반영합니다.
2. **복합 색인 확인** — `commands`(`state` + `createdAt`)가 없으면 명령이 안 가고, `events`(`childUid` + `at`)가 없으면 선택한 아이의 알림 목록이 비어 보입니다.
3. **릴리스 키스토어** — 지금 저장소의 것은 **개발용**입니다. 남에게 배포하기 전에 반드시 교체하고, 한 번 배포한 뒤에는 절대 바꾸지 마세요(업데이트가 막힙니다).

### 위치 문턱을 만질 때 (2026-08-17 이후)

이 앱은 **"수집은 넉넉히, 정리는 그릴 때"** 로 방침이 바뀌었습니다. 수집 단계에서 버린 점은 영영 못 살리지만 남긴 점은 언제든 다듬을 수 있기 때문입니다. 흔들림 제거는 `RoutePathRefiner`(오차 가중 평활 + 단일 스파이크 제거)가 그리는 쪽에서 합니다.

**문턱을 다시 조이고 싶어지면 먼저 이 셈을 해 보세요.** 이 저장소가 문턱 여섯을 한꺼번에 걷어낸 것은 전부 같은 이유입니다 — 아이의 보행 속도(1.0~1.3m/s)로 그 문턱에 도달할 수 있는지 확인하지 않았기 때문입니다.

| 시간 | 아이가 걷는 거리 |
|---|---|
| 5초 | **6m** |
| 10초 | 12m |
| 30초 | 36m |
| 1분 | 72m |

오차에 비례하는 문턱(`hypot(오차1,오차2)`)을 쓸 때가 특히 위험합니다. 오차 20m면 그것만으로 28m라, **5초 문턱에 걸면 걷는 아이가 통째로 사라집니다.** 오차 연동이 필요한 자리는 "제자리 흔들림과 구분해야 하는 곳"(변위 증거 판정)이지 "경로점을 남길지"가 아닙니다.

제자리 흔들림을 막는 책임은 **상류의 `AdaptiveMovementDetector`** 에 있습니다. 판정기가 정지라고 하면 `MovementTrailFilter`는 한 줄도 기록하지 않습니다. 아래쪽 필터를 다시 조이기 전에 위쪽이 이미 하고 있는 일인지 확인하세요.

그리고 **`SegmentBuilder.STAY_RADIUS_METERS`를 올리지 마세요.** 지도의 경로선은 MOVE 구간에만 그려지므로, 이 반경이 커지면 그 안의 모든 이동이 머무름 하나로 묶여 **선이 아예 안 그려집니다.** 100m 였을 때 반경 100m 생활권 아이의 하루가 통째로 사라졌습니다.

### 화면을 새로 만들거나 고칠 때 (2026-08-18 이후)

**값은 `res/values/dimens.xml` 에서만 가져옵니다.** 화면 좌우는 `@dimen/edge` 하나이고 머리말도 카드도 그 선에서 시작합니다. 이 표가 없던 동안 파일마다 손대는 사람이 그때그때 정했고, 그래서 같은 앱 안에서 화면 좌우가 14·16·20dp 로, 목록 줄이 5·12·14dp 로 갈렸습니다. 새 값이 필요하면 먼저 거기 이름을 붙이고 기존 것과 무엇이 다른지 한 줄 적습니다.

**지도 탭은 예외입니다.** 지도 위에 카드가 뜨는 구조라 좌우 여백의 뜻이 다르고, 지금 모양이 좋다는 평가를 받았습니다. 통일한다고 건드리지 마세요.

**눈이 아니라 자로 확인합니다.** 눈으로는 "대충 맞는 것 같은데"가 되지만 재면 42px 과 214px 이 나옵니다. 스크린샷을 뽑아 각 줄의 왼쪽·오른쪽 끝을 세는 것이 가장 빠릅니다.

```bash
adb -s <기기> shell screencap -p /sdcard/s.png && adb -s <기기> pull /sdcard/s.png
```

측정할 때 **화면 맨 왼쪽 x<30 은 빼세요.** 삼성 엣지 패널 손잡이가 그 자리에 겹쳐 찍혀서 앱의 왼쪽 끝인 줄 알고 8px 이라고 읽게 됩니다.

**그림을 넣기 전에 이미 무엇을 쓰고 있는지 셉니다.** 마스코트는 `mascot_3d` 입니다(아홉 군데가 씁니다). `ic_mascot` 은 납작한 옛 벡터라 새 화면에 쓰면 그 화면만 다른 얼굴이 됩니다.

**줄을 맞춘 다음에는 반드시 밀도도 잽니다.** 격자만 맞추면 "정리는 됐는데 헐렁한" 화면이 됩니다. 한 화면에 목록이 몇 줄 들어가는지 세고, 내용이 아닌 것(제목·설명·버튼)이 화면의 몇 %인지 봅니다. 예약 탭은 그 값이 한때 73%였습니다.

## 알려진 제약

- **집에서 40m 안에서만 노는 것은 선이 안 그려집니다.** 점은 다 저장되지만 한 머무름으로 묶이고, 지도의 경로선은 장소와 장소 **사이**에만 그려집니다. 반경을 더 줄이면 실내 GPS 흔들림이 머무름을 잘게 쪼개기 시작합니다.
- **아주 짧고 가까운 외출은 나가는 길이 얇습니다.** 집 앞 60m 놀이터라면 걸어가는 1분 동안 점이 1~2개일 수 있습니다. 정지 주기가 1분이라 그 사이에 좌표가 한 번 들어오는 정도입니다. 체류와 돌아오는 길은 제대로 찍힙니다. 더 촘촘히 하려면 정지 주기를 20~30초까지 내려야 하는데 배터리 대가가 큽니다.
- **공휴일 계산은 기기의 ICU 달력에 기댑니다.** 음력 환산이 한국 시각이 아니라 중국 시각 기준이라 아주 드물게 하루가 어긋날 수 있고, 기기의 ICU 가 이 달력을 못 다루면 그 해 공휴일이 통째로 빕니다(그때는 예약이 요일대로만 돕니다 — 넘겨짚지 않습니다). 맞게 계산했는지는 예약 탭의 '다음 쉬는 날' 한 줄로 확인하세요.
- **공휴일 스위치는 규칙 전체에 걸립니다.** 규칙별로 "이건 공휴일에도 돌아라"를 지정할 수는 없습니다. 밤 무음까지 공휴일에 함께 쉽니다.
- **GPS가 거친 곳에서는 짧은 외출을 놓칠 수 있습니다.** 변위 증거 문턱이 `max(50m, hypot(오차1,오차2)×1.5)`라, 실내에서 오차 40m로 잡히면 문턱이 85m로 올라가 60m 외출은 안 잡힙니다. **일부러 그렇게 뒀습니다** — 문턱을 더 낮추면 가만히 서 있는 폰이 5초 기록을 계속 켜서 배터리만 태웁니다. 못 믿을 좌표로 추측하느니 활동 인식과 지오펜스에 맡깁니다.
- **재설치하면 가족이 깨집니다.** 익명 로그인이라 앱을 지우면 ID가 바뀌는데 양쪽 다 되돌릴 길이 없습니다. 아이 폰에 "다시 연결" 버튼을 다는 것은 **아이가 스스로 감시를 풀 수 있게 된다**는 뜻이라 설계 판단이 필요해 보류 중입니다.
- **하루 구분을 아이 폰 날짜로 찍습니다.** 아이가 폰 날짜를 하루 앞으로 돌리면 그 뒤 기록이 부모가 못 가는 날짜에 저장됩니다. 보안 규칙으로는 막을 수 없습니다(서버가 대조할 기준이 없는 클라이언트 값이라).
- **아이가 앱을 강제 종료하면 전부 멎습니다.** 막을 방법이 없어서 막지 않고, 대신 부모 화면에 배너로 알립니다 — 위 ["아이가 앱을 강제 종료하면"](#아이가-앱을-강제-종료하면--막을-수-없고-대신-부모에게-알립니다) 참고.
- **7일 넘게 통신이 끊기면 그 초과분의 알림이 사라집니다.** 위치 기록은 멀쩡히 올라가는데 "학교에 도착했어요" 같은 사건만 서버가 거부합니다(보안 규칙이 사건 시각을 과거 7일로 묶고 있어서). 앱도 부모도 알아챌 수 없습니다. 원래 24시간이었는데 폰을 하루만 꺼놔도 그 사이 알림이 통째로 사라져서 7일로 넓혔습니다 — 넓힌 근거와 하한을 아예 없애지 않은 이유는 [`docs/known-issues.md`](docs/known-issues.md) 20번에 있습니다.
- **아이가 그럴듯한 거짓 알림을 만들 수 있습니다.** 아이 폰은 이 앱의 접속 키를 갖고 있어서 앱을 거치지 않고 사건을 직접 쓸 수 있습니다. 막으려면 사건을 폰이 아닌 곳(유료 요금제)에서 만들어야 합니다 — 받아들이기로 한 것이지 놓친 것이 아닙니다(known-issues 15번).
- **아이 폰의 하루 종일 실사용은 아직 미검증입니다.** 보호자·아이 역할의 실기기에서 설치와 적응형 서비스 시작까지 확인했지만, 삼성 절전 정책이 하루 동안 서비스를 유지하는지와 실제 배터리 소모는 장시간 들고 다녀야 확인할 수 있습니다.
